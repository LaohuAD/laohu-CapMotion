# 制作流程

本文件定义第二遍正式录制交接后的后期流程。第一遍自由录制仍由“老胡文稿”在原任务中调用 `scripts/cap-project-asr.mjs`，不进入本后期任务。

## 1. 建立作品控制文档

每条作品都应先建立或更新：

```text
作品/编号_主题/控制文档.md
```

这个文件是给执行 AI 读取的单作品有限自由度执行蓝图，用来记录：

- 当前作品的目标和观众。
- 用户对当前版本不满意的地方。
- 本轮必须优化的方向。
- 哪些 PPT / 口播 / ASR 内容必须被画面吸收。
- 每个场景的主标题、副标题和必须出现的文字。
- 每个场景的排版结构、图形关系、动效节拍和停留要求。
- Remotion、数字人、录屏、证据和 AI 视频的画面职责。
- 哪些内容必须严格执行，哪些内容允许执行 AI 在边界内调整。
- 质检标准和输出要求。

后续用户每次提出新的控制意见，都应优先更新 `控制文档.md` 或当前作品的分析/输出记录，再进入具体工程修改。这里的“控制意见”不只指控制文档更新，也包括普通对话里的修改要求、效果纠偏、审美判断、口头偏好和临时补充方向。这样 002、003 等作品也能继承“用户如何控制画面变好”的经验。

### 用户指令后的经验分流

每次用户提出作品修改指令、控制意见、审美判断、效果纠偏或更新控制文档后，必须先做一次经验分流：

```text
只影响当前作品的要求 -> 写回当前作品/控制文档.md、分析/、输出/
对后续作品也有效的要求 -> 写回 规范/ 或 知识沉淀/
可复用的画面结构或组件 -> 写回 规范/组件规则.md，必要时沉淀到 模板/
```

执行前要问自己：

```text
这条要求是不是用户长期偏好？
这条要求是不是以后同类作品也要遵守？
这条要求是不是一种可复用组件或模板？
这条要求是不是一个踩坑或禁区？
这条要求是否和旧规则冲突？如果冲突，是否应以新要求覆盖旧规则？
```

如果答案是“是”，就不能只修改当前 `制作/index.html`，必须同步更新项目级文档。

用户实践经验不需要先证明“绝对正确”才能沉淀。当前项目以用户最新实践要求为准；如果后续新经验推翻旧经验，应更新旧文档，把旧规则覆盖、删除或标注为已替换，而不是让冲突规则长期并存。

## 2. 收集输入

单条作品的 `输入/` 目录只保存文字型输入和素材索引：

```text
script.md        口播稿
asr.json         ASR 时间轴
素材索引.md       口播视频、音频、PPT、截图等外部素材的绝对路径与基础信息
references.md    案例、风格参考及其外部路径说明
```

视频、音频和其他大媒体不复制进项目；制作时直接读取素材索引中的外部绝对路径。必须临时转码时使用 `/tmp` 或任务专用临时目录，结束后清理。

不是每次都必须全部具备。若没有 ASR，则先按口播稿做章节级时间轴。

## 3. 内容分析

输出到 `分析/`：

```text
内容分析.md
画面补充策略.md
动画节拍.md
分镜.md
画面规划.md
时间轴.md
```

如果输入中有 SRT，优先新增：

```text
SRT时间轴.md
```

并按第二遍真实配音建立 S2 源时间；EDL 冻结后生成 T2 成片时间，覆盖任务不得继续沿用草稿或第一遍时间轴。

分析重点：

- 口播主线是什么？
- 哪些地方需要结构化？
- 哪些地方需要例子？
- 哪些地方适合做流程、对比、公式或清单？
- 哪些内容可以合理补充口播没有展开的信息？
- 哪些内容需要额外资料或用户确认？
- 哪些内容不要上屏？
- 每个场景应该拆成哪些 ASR 对齐的动画节拍？
- 哪些信息要逐步出现、连接、点亮、变化或收束？

## 4. 制作 Remotion 与外部覆盖素材

进入制作前，先按 `模板/口播精剪审稿模板.md` 将虚拟成片字幕、讲解单元、动画效果与预期显示时间、素材用途和全部疑难放入同一份审稿文档。用户参谋和图片反馈直接写回对应方案，整份当前修订批准后才执行剪辑或动画制作；不是先剪完再交动画方案。批准后的工程细化保持已确认的观看效果，若需改变则返回审稿。

项目内只保存配置、任务包和文字记录：

```text
production-package.json
remotion-configs/
素材索引.md
覆盖质检.md
```

原则：

- 先冻结 EDL 和 S2→T2 映射，明确每个元素对应的 T2 时间点。
- 再从 `规范/动画效果库.md` 选择动画模型和动效名词，避免只写“做酷一点”。
- 再完成静态布局。
- 再加入 Remotion 帧驱动动画。
- 动效应遵守 `规范/MG动画表达方法.md`、`规范/动效规则.md` 和 `规范/动画效果库.md`。
- 多场景使用可复用 Remotion composition。
- 画面素材统一放入 `assets/`。
- 作品中跑通的组件经验要回写到 `规范/组件规则.md`。
- 不允许场景开头一次性展示全部信息，除非这是刻意设计的总览画面，并且后续仍有焦点变化。

### 4.1 Remotion 组件工作流

Remotion 是新任务唯一程序动画引擎，可独立成片或进入 Cap Motion 上层轨。固定步骤：

```text
1. 后期向 laohu-animation-director 提供请求范围内的虚拟成片连续文字、保留片段/词级映射、底画和源材料。
2. 先形成讲解单元与画面安排：组合哪些片段、是否采用动画、实际覆盖起止、局部或全幅、素材需求；未冻结时标为草案。
3. 对选中的动画单元转译具体画面与语义节拍，给内容标来源，纳入同一份剪辑审稿；吸收用户反馈并取得当前整份方案批准。
4. 批准后冻结 EDL，按冻结 T2 校验已确认窗口与内部动作，编译正式合同，再选复用、组合或作品专属 Composition；不限定已有家族，使用所选实现的真实 Zod schema。
5. 在共享 workspace 预览并渲染 standalone / asset / both。
6. 截图检查入场、展开、收束、最终态和手机缩略可读性。
7. 需要长期保留的媒体成品输出到主输入媒体所在目录；当前作品输出目录只记录成品绝对路径、参数和质检结果。
8. 以冻结 T2 时间和 Cap expectedRevision 写入上层 Motion 轨，revision 冲突时停止。
```

共享目录：`模板/remotion-assets/workspace/`。不要在每条作品重复安装 `node_modules`。

## 5. 覆盖任务选择与总装

制作脚本可先建议 `BASE / SCREEN_RECORDING / EVIDENCE / REMOTION / AVATAR / AI_VIDEO`。后期总装与动画导演按剪后实际讲述、底画证据及已锁定决定复核；粗建议不直接成为最终覆盖范围，未标动画的讲述也纳入请求范围内的画面判断。先保留底层基础视频和主音频，再把已验收素材写入上层覆盖轨。

任务包必须记录 T2 时间段、承担的解释职责、输入、输出格式、透明需求、停留时长和验收。先删除或降权重复表达，再接入覆盖；禁止重复贴片。

具体路由见 `.agents/skills/laohu-video-postproduction/SKILL.md`。

媒体导出到主输入媒体所在目录。完整剪辑流水线默认只保留最终成片，例如：

```text

```


## 8. 口播精剪流程

当用户给出口播视频和 SRT / ASR，要求根据字幕剪辑视频时，优先使用“审稿决策 -> 剪辑清单 -> 技术导出 -> 复查验证”的流程。这个流程吸收自 `参考项目/roughcut-pipeline` 的工作流思想，但本项目只复用流程结构和判断方法，不直接复制其非商业许可证代码。

当前已验证的文字识别基准是剪映 SRT。Apple Speech 已退出工作流，不作为主识别、第二识别源、置信度比较或交叉校对来源。用户提供剪映 SRT 时，直接以剪映文字为主稿；未经用户当轮许可，不操作剪映或其他 GUI。

需要从本地媒体全自动重新识别时，项目技术默认是火山引擎“大模型录音文件识别极速版”HTTP API。符合 2 小时、100MB 限制的本地音频使用 Base64 `audio.data` 直传，不需要临时媒体 URL；已有受控 HTTPS URL、文件超过极速版限制或用户明确优先低成本时，改用标准版。接口返回的原始 JSON 必须保留，SRT 由分句或逐词毫秒时间戳转换生成。

固定执行入口为 `.agents/skills/volcengine-asr-srt/`。该 skill 统一承担极速版直传、标准版 URL、JSON 转 SRT、SRT 时码校验和 `16kHz` 单声道 MP3 抽取；后续不得为单条作品复制一套调用代码。

用户提供的旧 SRT 只是比较输入，不是跳过新 ASR 的理由。完整流程固定为：

```text
原始媒体重新识别 -> 新原始 ASR / SRT
-> 三信号分析并建立虚拟粗剪 EDL
-> 在同一时间映射上完成虚拟精剪、重排和文字决策
-> 确认会影响剪口、保留范围或顺序的疑难项
-> 冻结 EDL -> 只渲染一次无字幕成片
-> 按风险决定完整成片重识别或 EDL 映射加剪口抽查
-> 确认只影响字幕文字的疑难项 -> 发布 SRT -> 按需烧录
```

粗剪阶段不能只用“有没有 ASR 文字”和“有没有波形”两个信号。必须同时判断：词级文字及时间、波形与声音类型、画面变化和前后语境。`有文字但声音异常弱` 且只持续约 `1-2` 秒时，可提高其作为气口、误识别或废弃试说候选的优先级；无文字区间持续较长，而且存在连续声音或画面变化时，应提高其作为作品、音效或操作演示的概率并默认保护。时长是辅助权重，不是删除开关。

用户明确触发“字幕的烧录”后，调用 `.agents/skills/burn-subtitles/`。烧录是发布 SRT 之后的独立交付阶段，默认只生成中英双语版；只有用户明确要求中文版时，才额外或单独生成中文单语版。首次采用或改变样式时，先生成一份双语短预览，用户确认后再输出全片；用户指定样片时长时按指定值执行，未指定时约 10 秒。它不是粗剪、精剪、修正字幕三个阶段的并列版本。

这是一条串行流水线，不是要求分别交付“粗剪版、精剪版、字幕修正版”。默认只把完成全部请求阶段的成片和发布 SRT 作为交付结果；粗剪、未校对精剪和修正草稿只服务下一阶段，放在 `/tmp` 或任务临时目录，验证最终结果后删除。只有用户明确要求阶段验收、前后比较或单独交付时，才保留对应中间产物。若用户只要求其中一个阶段，则严格停在该阶段，不自动扩大任务范围。

内部阶段默认采用“先把决定算清楚，再渲染”的虚拟剪辑方式。粗剪和精剪先形成可追溯 EDL，不分别导出媒体；会改变保留区间、剪口或顺序的疑问必须在 EDL 冻结前确认。无字幕成片只渲染一次并先验证音画同步；错别字、展示断句、口语清理和英文翻译等文字问题在烧录前确认即可。复杂重排、大量短剪口、同步异常或映射冲突时，对无字幕成片完整重新 ASR；简单且映射可靠的顺序剪辑，可使用 EDL 映射配合剪口重点抽查。

“重新识别”与“选择发布主文本”是两个决策。新的云 ASR 未通过与剪映的人工样本验收前，不得自动替换剪映主稿；不得为了证明新流程可用，强行选择质量较差的识别结果。

豆包输入法可以作为“黑盒识别器”纳入长期流程，但不要把它误当成字幕 API。豆包输入法的常规能力是把麦克风语音输入成文字，通常不直接返回句级时间戳；若要生成 SRT，需要外部程序先用 FFmpeg / VAD 把音频按人声停顿切段并记录每段起止时间，再把每个小片段通过虚拟麦克风喂给豆包输入法，收集文字后与外部时间轴合成 SRT。没有 BlackHole、Loopback 等虚拟音频设备时，不要承诺自动喂音频文件给豆包输入法；不建议逆向豆包私有语音接口。

剪映没有对外公开、稳定的命令行字幕接口。因此默认不把剪映当作无界面文件 ASR，也不复制它的模型或调用私有 `SpeechSDK_*` ABI。只有用户在当轮明确要求使用剪映识别，并且运行环境确实安装了兼容版本时，才能进入 `.agents/skills/jianying-srt-bridge/` 的独立临时草稿流程。

部分新版剪映的时间线 `draft_info.json` 已加密，不能把“读取草稿 JSON”作为正式字幕提取方案。用户未授权界面操作时，不创建或修改任何剪映草稿；只有已配置并通过验收的文件式云 ASR 才能承担自动新识别。

### 8.1 文件式云 ASR 接入约束

火山引擎录音文件识别同时保留极速版同步流程和标准版异步流程。默认接入原则：

```text
本地视频 -> FFmpeg 抽取单独音频 -> 检查格式、时长和大小
-> 符合极速版限制：Base64 直传 -> 一次请求返回结果
-> 不符合或明确优先低成本：受控 URL -> 标准版提交/轮询
-> 保留原始 JSON -> 转换原始 SRT -> 校验 -> 删除临时音频和云端对象
```

- 私密凭据默认从 `~/.config/laohu/volcengine-asr.env` 读取。该文件存在且变量完整时直接调用；只能加载变量，不能打印文件内容或在调试日志中回显请求头。
- 使用者必须自行配置并验证火山引擎凭据和资源权限。项目脚本优先使用新版 `API Key -> X-Api-Key` 鉴权，同时保留旧版 `APP ID + Access Token` 鉴权作为兼容能力。所有凭据只能存在项目外的私密配置中，不得进入 Git、日志或回复。
- 极速版资源 ID 固定为 `volc.bigasr.auc_turbo`，标准版使用 `volc.seedasr.auc`。旧配置中的 Secret Key 不参与这两个录音文件识别接口，不得误放进请求头。
- 默认只使用账户已有的免费或预付额度，不自动开通后付费、不自动购买资源。额度不足或控制台要求进入计费时，停止任务并先说明预计成本、替代模式和是否继续。
- 官方返回 `45000030 requested resource not granted` 时，说明凭据已到达语音服务，但当前应用尚未开通 `volc.bigasr.auc_turbo`。此时不轮换凭据、不开通 TOS；应在火山控制台确认极速版计费条款并开通资源后重试。
- 不要根据用户从“新控制台页面”还是“旧控制台页面”取得凭据来猜鉴权方式，应根据凭据字段判断。旧版鉴权仍可用于已验证的标准接口，但不得在新版 API Key 可用时覆盖它。
- 极速版支持 WAV、MP3 和 OGG OPUS，最长 2 小时、最大 100MB；官方建议二进制直传尽量在 20MB 以内，这是传输建议而不是硬性上限。MP4、M4A 等本地媒体先抽取或转码，不直接冒充受支持格式。
- 开启 `show_utterances` 以获得分句和逐词时间戳；开启标点与数字规整以提高可读性。
- 默认关闭 `enable_ddc` 语义顺滑。该能力会删除或改写停顿词、语气词和语义重复词，不适合作为粗剪、精剪的原始证据；内容精简由剪辑决策层完成。
- 可按项目维护热词、替换词和上下文，优先覆盖人名、账号名、软件名、模型名、英文缩写和行业术语。
- 极速版 Base64 直传不创建云端对象。只有标准版 URL 模式需要临时上传时，才必须获得用户对目标云服务的授权；识别成功或失败后都要删除临时对象。
- 即使同属字节跳动，也不能宣称该 API 与剪映或豆包输入法使用完全相同的模型和后处理。只有人工校对基准能决定是否切换主 ASR。

### 8.2 建立剪辑简报

在当前作品 `分析/` 下先建立或更新剪辑简报，内容包括：

```text
源视频：
字幕 / ASR：
目标时长：
观众：
输出风格：
必须保留：
可以删除：
主线一句话：
4-7 个故事节点：
删除策略：
待用户确认：
```

如果用户没有给目标时长，不要臆造一个硬时长。可以先按“去掉空白、重复、废弃试说，同时保证完整度”的默认目标执行；如果用户明确要压缩到某个时长，再按目标时长估算保留比例。

剪辑简报完成后、生成任何真实 EDL 或操作媒体之前，必须先在文档中完成一次全流程虚拟剪辑：先按两类音频证据做虚拟初剪，再做重复试说与内容取舍的虚拟精剪，随后完成字幕切分和保真顺句。预剪辑字幕审稿文档必须覆盖整条源视频，按候选剪辑片段逐项列出：片段编号、源开始 / 结束时码、ASR 原文、建议 `保留 / 删除 / 待确认`、理由；会形成独立剪口的长气口、无字幕声音和演示候选也要单独列出。字幕切分不能继承 ASR 条目边界，必须先跨相邻条目还原连续词流，识别上一句的尾巴、下一句的宾语以及被分开的完整术语。

文档的核心预览是“按当前方案剪完后的字幕时间轴”：按最终播放顺序逐段列出连续计算的目标开始 / 结束时码、对应源时码和拟用字幕，让用户在没有真正剪视频前就能阅读最终成片。每条拟用字幕应像正常人写出的完整表达：允许在语义等价范围内跨条目移动功能词、删除重复起头并调整书面语序，但不得改写事实、观点、比较关系或限定条件；模型名、版本号和术语组合必须作为不可拆原子。文字错词、专名、数字、语序、字幕切分、字体和双语样式疑难集中放在同一份文档中，不让用户在多个过程文件间来回寻找。

审批是硬门槛：用户必须看过整份虚拟成片时间轴并明确批准，所有会改变媒体保留范围的疑难必须先解决，才允许把虚拟决定写成可执行 EDL 并操作媒体。只影响最终文字的疑难也应在进入剪辑前尽量确认；若用户明确同意延后，只能延到字幕烧录前，不能静默猜测。文档未批准时不得渲染样片、无字幕成片或正式成片。

### 8.3 生成审稿决策

不要直接把字幕时间码丢给 ffmpeg 就完事。先按字幕行或语义单元生成审稿决策：

```text
subtitleId / start / end / text / status / reason
status = 保留 / 删除 / 待确认
```

判断顺序：

1. 先按主线和故事节点确认必须保留的信息点。
2. 再找重复试说、口误重说、空白停顿、弱过渡和离题支线。
3. 对每个删除写出具体理由。
4. 读取只保留内容形成的大纲，检查是否像一条完整内容，而不是散碎高光。
5. 检查每个话题入口是否有背景，每个转折是否有前因，每个结论是否有落点。

当前项目的默认偏好是：内容完整度优先于压缩冗余。尤其是只出现一次的背景、活动信息、关键论据、转折、限定条件、情绪表达和完整句尾，不能为了剪短误删。

删除决策必须落到最小语义单元，禁止按“整条 SRT、整组 cue 或整个场景标签”一刀切。一个条目里可能同时包含推广场景与有效说明、口水话与方法总结、互动引导与新框架；只能删除已经证明无价值的那一部分。出现“推广、下一期预告、过程说明、口水话”等标签时，必须继续逐句检查其中是否含有答案入口、适用边界、方法框架、人格信息、转化动作或资源说明。转化动作和互动引导不是天然口水话，是否删除属于发布策略；用户未明确要求去推广时，默认保留或列为待确认。

当一条视频同时包含讲话与作品播放时，录制音频只分“麦克风声音、系统声音”两类；用户所说的外部录音归入麦克风声音。先检查麦克风是否有人物讲话，再检查系统声音是否持续有效；两者都无有效声音才优先进入气口 / 空白候选。系统声音持续存在时，再结合画面变化和前后语境判断是否为作品播放或操作演示，并按连续播放区间保护。仅凭区间较长、ASR 没有文字或页面有变化，不能命名为动画 / 演示；证据冲突时标 `待确认` 并询问用户。不能先按 SRT 生成删除区间，再把无字幕声音补回去，因为这种顺序容易切碎音乐和效果声。

初剪只删除已确认的气口、纯空白和无意义等待。精剪在初剪时间轴上处理失败起头、口误后紧邻重录、前一句录坏后后一句重说和可证明的同义重复；通常保留后面更完整自然的一版，但前一版只要包含独立信息、限定条件、情绪或操作同步价值，就不得整段删除。

精剪 EDL 冻结后，使用最终保留语音和词级时间重新派生展示字幕。字幕先跨越相邻 ASR 条目恢复连续词流，再按完整意群、自然气口和可读长度切分；在不改变事实、观点、重点和实际口播含义的前提下清理口语冗余、调整书面语序。切分后必须反查句尾残词、跨条目承接和专名完整性，禁止出现“完 / 整”“有 / 搭建能力者”或模型名被拆开的机械断句。除用户已确认的系统声音演示外，只要人物有效讲话，画面上就必须有对应字幕；字幕覆盖缺口必须在烧录前修复。最终使用用户已确认的中英双语、字体和格式，首次采用或改变样式时仍先给用户确认。

多人直播的音频处理放在最终合并之后：先用最大增益受限的动态归一化温和拉齐远程麦克风差异，再做两遍 EBU R128 响度校准。默认网络视频目标为 `-16 LUFS`、真峰值不高于 `-1.5 dBTP`、响度范围约 `7 LU`。第一遍只测量，第二遍使用测量值输出；不要对每个剪辑批次单独做响度归一化，也不要用强压缩破坏作品音乐。

### 8.3.1 精确剪辑的内容导演流程

用户明确要求“精确剪辑”时，在逐句审稿前增加内容导演阶段：

```text
1. 按源文件精确时长把全局 SRT 映射回各源视频。
2. 恢复 ASR 错词最可能表达的真实语义。
3. 提炼一条主线和 6-14 个顺序章节。
4. 为每段内容标记：知识价值、案例证据、适用边界、信任价值、人格价值、操作同步价值。
5. 找出后录补充应插入的章节，不默认沿用录制顺序。
6. 先输出章节级 EDL，再处理章节内部的重复和口水话。
7. 反向通读目标顺序，检查背景、转折、示例、结论和行动是否闭合。
8. 以粗剪 EDL 为内容完整性基线，自动列出“粗剪保留、精剪删除”的全部词级区间；逐项标记为明确冗余、发布策略待确认或独立信息点。存在未审查区间时，不得渲染精剪成片。
9. 若原录制已经沿清楚主线自然推进，保持原顺序和个人表达；“精剪”不自动授权改写讲述习惯、删除完整表达或重构章节。
```

精确剪辑中的“口水话”按功能判断，不按词面判断。在老胡口播中，它默认只指独立的“嗯、啊”、废弃起头、紧邻自我纠正和可证明的重复试说，不指讲述者的个人句式、展开方式或完整表达。承担举例、转折、因果、结论、人格或画面同步作用的内容必须保留。短词剪口必须有可靠音频边界，不能为了书面化牺牲自然口语和音画同步。

人物塑造和信任信息不能因为“不属于纯知识点”就当作口水话删除。讲述者对自己性格、做事方式、价值取向、过往经历、真实投入和情绪反应的描述，只要能帮助观众理解“这个人是谁、为什么可信、为什么会这样判断”，就标记为 `人格价值 / 信任价值` 并保留。真正应删除的是围绕这些内容出现的独立语气词、拖音、废弃起头、相邻重复词和没有增加新含义的同义绕述；不能连同人格信息本身一起删掉。

精剪的章节重排先做必要性检查：如果原片已经沿一条主线自然推进，只在章节内部压缩口水话和补足层级，不为了显得“做过内容导演”而强行换序。只有后录补充放错章节、结论先于依据、前置概念晚于应用，或原顺序会让陌生观众明显断线时，才调整章节顺序。连续软件操作和依赖界面状态的演示内部仍保持原序。

### 8.4 生成剪辑清单

审稿决策确认后，再生成技术剪辑清单：

```text
keepRanges:
  startMs:
  endMs:
  subtitleIds:
```

相邻保留片段之间是否合并，要看停顿和语义：

- 相邻讲话剪口默认保留合计约 `0.1–0.2` 秒真实气口，让前句自然收音、后句完整起音。
- 句子内部必要呼吸可以极短保留，但不要让观众看到明显思考和组织语言。
- 如果两句合起来才构成一个完整表达，要作为语义单元处理。
- 如果中间有废弃试说，即使有声音，也要拆开删除。

EDL 生成后还必须检查每个保留区间内部，而不是只检查保留区间的起点和终点。一个数秒的保留片段中仍可能夹着思考停顿或页面等待；如果内部同时没有有效文字、没有有效声音、也没有需要保护的画面动作，只删除波形确认的静音中段，并让拼接处保留约 `0.1–0.2` 秒真实气口。所有超过 `0.2` 秒的静音检测结果必须逐项标成“删除”或“保护”，不能只运行 `silencedetect` 后把结果留在日志里，也不能把 ASR 词级时码直接当成音频剪口。

### 8.5 导出方式

导出时优先从原始视频按 `keepRanges` 重切视频和音频，保持音画同步。不要只处理音频再套回视频，也不要只处理视频而让音频另走一条时间线。

项目级精确裁剪可使用 `workflows/laohu-video/模板/video-editing/precise-cut.mjs`：EDL 的 `precisionSequence` 可以混合字幕编号、编号范围和词级绝对时间段；工具会为每个保留区间成对执行 `trim / atrim`，再统一 concat，输出后把解析后的源时间、目标时间和时长写回同一份 EDL。每次成片仍必须单独做流、静音、时长和音画同步验证，不能把脚本成功退出当成交付验收。

当 `precisionSequence` 包含章节重排时，只能合并目标序列中相邻且源时间仍然向前推进的区间。后录片段前置后，下一段的源时间可能回到更早位置，这种情况必须保留为独立区间；禁止只用“开始时间小于上一段结束时间”判断重叠，否则会把重排后的多个章节误并成一个大区间。每次渲染前先运行 `--dry-run`，核对请求区间数、解析区间数和预计时长是否符合内容导演结果。

推荐策略：

```text
低风险短片段 -> 可用 concat / copy 快速试剪
最终交付或音画同步敏感 -> 使用精确重编码，确保每个片段音视频同时从原片裁出
多机位 -> 先确认主音频机位，再做同步检查，不要默认第一条素材就是主机位
```

数百个短剪口的最终成片还必须统一量化音画边界：视频按源帧编号裁切，音频按同一帧对应的采样点裁切。30fps / 48kHz 素材每帧对应 1600 个音频采样点。分批渲染时使用 PCM 保存中间音频，所有批次拼接完成后再统一编码一次 AAC；禁止每批分别编码 AAC 后直接用 MP4 stream copy 作为最终拼接。最终媒体时长与 EDL 预计时长的容差上限为一个视频帧加一个音频帧，超出时必须重建导出链路。

如果是多机位内容，必须先确认：

```text
主音频机位
每个机位有哪些文件
每个文件的顺序
哪些文件要排除
```

非主机位导出前要先做短预览同步检查，确认嘴型、动作和主音频一致后再全片导出。

### 8.6 验证与复盘

最终交付前至少检查：

```bash
ffprobe -hide_banner -v error -show_entries format=duration,size -show_streams -of json "$OUTPUT"
ffmpeg -v error -i "$OUTPUT" -map 0 -c copy -f null -
ffmpeg -hide_banner -i "$OUTPUT" -af silencedetect=noise=-35dB:d=0.15 -f null -
```

必须确认：

- 只有视频流和音频流，除非用户明确要求字幕流。
- 视频流和音频流起点正常，不能出现明显音画不同步。
- 没有 0.15 秒以上明显静默残留；若有，继续二次收紧。
- 静音复查必须覆盖每个 EDL 保留段内部；凡未被明确标记为作品播放、操作演示、情绪停顿或画面阅读时间的静音，都不能因为位于一个“大保留区间”里而漏删。
- 开头、中段、结尾画面不是黑屏或错素材。
- 被用户强调必须保留的句子和信息点确实存在。
- 已按风险选择成片校验方式：高风险成片的新识别结果已与 EDL 映射文本交叉检查；低风险顺序剪辑已完成 EDL 映射和剪口重点抽查。不能只验证 SRT 格式有效。
- 若成片 ASR 出现“就就是、用用”一类重复音节，优先改为完整短语或分句拼接；同一单字边界连续两次微调仍无效时，禁止继续追逐毫秒数。
- 双流起点应同时从 0 开始。若只有视频整体晚一个编码重排帧，先验证包连续性，再在最终无损封装中只重置视频包时间戳。
- 最终媒体时长与 EDL 预计时长之差不超过一个视频帧加一个音频帧；不能只比较最终音频流和视频流彼此接近，因为两条流可能一起继承了批次累计误差。

如果 ffmpeg 出现时间戳警告，不要只凭警告下结论。先验证播放、抽帧、时长、音画同步和 demux；只有这些失败时，才需要换精确模式或重建剪辑方案。

### 8.7 磁盘与临时文件清理

长视频精剪、Remotion 渲染和 Cap 导出都可能在短时间内生成大量中间文件。执行这类任务时，不要只关注导出是否成功，也要把磁盘占用当成流程的一部分管理。

固定要求：

- 视频剪辑与媒体渲染采用“媒体就近交付、项目只留文字记录”：完成用户要求的全部阶段后，只把最终媒体输出到主输入媒体所在目录；内部粗剪、未校对精剪、分片和测试渲染放在临时目录并及时删除。本项目的 `输入/`、`分析/`、`输出/` 不保存视频或音频二进制文件。
- 项目 `输入/` 用素材索引记录原始媒体的绝对路径，不复制原始媒体；项目 `输出/` 只保存交付报告、成片 ASR/SRT、EDL 映射、质检数据等文字型记录，并在报告中记录外部成片绝对路径。
- 临时媒体只允许放入 `/tmp` 或明确的任务临时目录，完成完整解码、音画同步、响度、静音和成片 ASR 复查后立即清理。

- 开始前先看 `df -h`，确认剩余空间足够；长视频任务如果只剩几 GB，不要直接启动大规模重编码。
- 中间 WAV、分片、chunk、临时 concat 文件、失败输出和测试输出用完即删。
- 当前作品只长期保留：原始输入索引、必要分析文件、文字型输出和质检记录。最终或当前可用的媒体输出放在主输入媒体所在目录，不在项目内长期保留；不要保留失败版本。
- 大视频、渲染结果和临时文件不要进入 Git 跟踪范围，也不要让 Git 对这些文件反复打包。
- 如果磁盘突然从十几 GB / 二十几 GB 变成接近满盘，优先检查 Git 临时垃圾：

```bash
git count-objects -vH
find .git/objects/pack -maxdepth 1 -name 'tmp_pack_*' -type f
find .git/objects -mindepth 2 -maxdepth 2 -name 'tmp_obj_*' -type f
```

当 `git count-objects -vH` 显示 `garbage` 或 `size-garbage` 很大，并且确认没有 `git / pack-objects / index-pack` 进程运行时，可以清理这些 Git 临时垃圾。不要把用户原始视频、当前有效输出或应用数据当成临时文件误删。

收尾时至少执行一次：

```bash
df -h .
find 当前作品目录 -type f -size +100M -print
git count-objects -vH
```

发现异常占用时，先说明来源和大小，再决定是否删除；对用户原始素材、微信/QQ/飞书/浏览器数据等应用资料，必须先确认再处理。

## 9. 复盘沉淀

每轮控制文档执行后，即使作品还没有完成，也必须整理：

在这一步之前，执行 AI 应先按场景结束帧自行截图、自检和比对。若发现空白、遮挡、断行、信息不足、重点不清、讲解价值不够，必须先在本轮内修正，再进入复盘。用户指出的问题要记，AI 自己发现并修正的问题也同样要记。

```text
哪些画面有效？
哪些画面只是复述口播？
哪些补充信息有价值？
哪些补充信息太发散？
哪些动效提升了理解？
哪些动效显得廉价或抢戏？
哪些组件可以沉淀为模板？
哪些片段适合交给 Remotion，哪些保留录屏更清楚？
Remotion 输出是否按冻结 T2 和 Cap revision 正确写入上层轨？
用户明确喜欢什么？
用户明确不喜欢什么？
本轮用户指令里哪些新要求已经成为项目级规则？
哪些要求只适用于当前作品？
```
