# 画面排版与审美标准

本文件回答一件事：**口播教学视频里叠在底画上的文字、图形、卡片，按什么数字做才不廉价。**

适用场景是屏幕录制底画 + 右下角摄像头小窗 + Remotion 叠加层。所有条目写成可直接填进代码的数值，并标注来源可靠性。

## 0. 可靠性分级与适用边界

| 级别 | 含义 | 本文件里的例子 |
| --- | --- | --- |
| **A 官方规范** | 标准组织、监管机构或平台方发布的成文规范 | WCAG 2.2、EBU R95、GY/T 357—2024、GB/T 15834—2011、W3C clreq、BBC Subtitle Guidelines |
| **B 厂商文档** | 大厂公开的设计系统文档 | Material Design 3、Apple HIG、Google Fonts、Adobe 字体 ReadMe |
| **C 当事人公开说明** | 创作者本人公开讲过的做法 | manim 文档、博主对自身字体的公开说明 |
| **D 从业者共识/观察** | 行业惯例、第三方拆解、无成文规范 | 「一屏一个强调色」、卡片泛滥的批评 |
| **E 未找到可靠依据** | 网上说法矛盾或没有出处 | 见第 9 节 |

**三条适用边界必须先说清，否则数字会被用错：**

1. **WCAG 的对比度条款在字面上是给网页和 App 的**，它的定义域是「由用户代理呈现的内容」。视频画面不是网页。但 1.4.3 的原始依据是 ISO 9241-3 和 ANSI/HFES 100-1988 的显示终端人体工学研究，这两份研究讲的是屏幕阅读本身，所以把 4.5:1 / 3:1 借用到视频画面是**有实验依据的外推**，不是标准原文要求。本文件把它当作最低门槛使用。
2. **BBC、Netflix 的字幕规范是给字幕（subtitle/caption）的**，不是给动画卡片的。字幕属于「观众必须读、且不能选择不读」的文字，约束比卡片更严。本文件把字幕的数值当上限使用：卡片正文可以比字幕标准略小，但不该比它更宽松。
3. **GY/T 357—2024 是 4K 超高清（3840×2160）电视剧母版标准**。它的百分比可以直接换算，它的像素值（80px）只对 4K 成立。

## 1. 专业科普/解说视频在画面文字上的共同规律

### 1.1 可量化的共同规律

| 规律 | 数值 | 依据 |
| --- | --- | --- |
| 一屏信息只讲一件事，文字是配角 | 一屏最多 3 级文字（主标题 / 支撑说明 / 微标签），第 4 级必须去掉 | D。三级结构来自这些作品的稳定外观，未见成文规范 |
| 屏幕阅读速度按 238 wpm 估算英文 | 拉丁字母平均阅读速度 **238 wpm**（英语单语研究 236 wpm，西班牙语 278 wpm），此前流行的 300 wpm 高估约 26% | A。Brysbaert 2019，190 项研究、17 887 人、1901—2019 年 |
| 中文按 300 字/分钟起步，正式内容留 50% 余量 | 《义务教育语文课程标准》第三学段要求「默读一般读物每分钟不少于 300 字」。这是**最低能力线**，不是舒适阅读线 | A。课标原文；用于视频时按 150—200 字/分钟设计更稳 |
| 字幕每行字数 | 中文 **23 字/行**为交付硬限，Netflix Originals 收紧到 **16 字/行** | A。Netflix Partner Help Center |
| 字幕每屏字数 | 中文 **不超过 14 字**（含符号），对白字幕不超过 2 行 | A。《无障碍音视频出版物通用技术规范》（GB/T 征求意见稿，2025-09-12）6.3.1 / 6.3.7 |
| 字幕停留 | **3—5 秒**；最短不低于 0.3 秒/词（4 词 ≈ 1.2 秒） | A。同上 6.3.8；BBC Subtitle Guidelines 4.1 |
| 字幕最大行数 | **3 行**（BBC），中文对白字幕 2 行 | A。BBC 19.6 |
| 字幕字号（横屏） | 行高 = 有效画面高度的 **7%—8%**，7.5% 为可用值 | A。BBC 9.2.1 |
| 字幕字号（竖屏） | 行高 = 有效画面高度的 **3.9%—4.5%**，4.2% 为可用值 | A。BBC 9.2.1 |
| 字幕区高度（4K 电视剧） | 对白字幕矩形区域 = 垂直方向有效画面高度的 **10%** | A。GY/T 357—2024 9.1.2 |
| 字幕字身高度（4K 电视剧） | 对白字幕高度 = 有效画面高度的 **5%，容差 ±1%** | A。GY/T 357—2024 9.3.1 |
| 图形安全边距 | 全部图形必须在 **Graphics Safe Area** 内：上下左右各内缩 **5%**；关键动作内缩 **3.5%** | A。EBU R95（2017 版）Note 5 |
| 片头片尾字幕安全区 | 不超出有效画面水平、垂直方向各 **80%** 长度所包围的区域 | A。GY/T 357—2024 9.1.1 |
| 字幕与语音的起点误差 | 落在语音首帧上，容差 **1—2 帧** | A。Netflix Subtitle Timing Guidelines §1 |
| 字幕与语音的终点余量 | 对话结束后至少再留 **0.5 秒** | A。Netflix §1 |
| 连续字幕之间的间隔 | 至少 **2 帧**；24fps 下 3—11 帧的间隔必须收到 2 帧或放到 0.5 秒以上 | A。Netflix §5；《无障碍音视频出版物通用技术规范》征求意见稿 6.3.6 要求至少 2 帧间隔 |
| 双语字幕的中西文之间 | 加 **¼ 全角空** | A。W3C clreq 6.3.3；C。少数派盘点记录 iOS 系统字幕同样在中西文之间加 ¼ 全角空 |

### 1.2 一条贯穿性判断

这些作品真正一致的不是「用了什么字体」，而是**一个画面只有一块区域在要求观众阅读**。

Vox 的做法被第三方拆解为「扁平化设计 + 有限调色板」；3Blue1Brown 的动画节奏由 manim 的 `run_time` 直接控制，默认 1 秒、默认 `smooth` 缓动，创作者可以把某个动画显式设为 `lingering` 来「停留」。这些都是**用参数把注意力分配到时间轴上**，而不是在一帧里塞满。

对你的场景，翻译成一条硬规则：

> 底画已经是屏幕录制（本身信息量就大），所以叠加层在任何一帧里，**需要被读的文字总量不超过 30 个中文字**。超过就拆成两拍出现。

这条是 D 级（观察 + 上述规范反推），但它是本文件里最能直接消除「程序员默认值感」的一条。

## 2. 字体层次

### 2.1 一个画面需要几级文字：五级，实际最多用三级

对外发布物的标准层级是五级。但在一个画面里同时出现，**建议不超过三级**；五级是为整片不同场景复用而设。

基准关系：以正文 `B` 为 1.0，各级比例如下。

| 级别 | 用途 | 相对正文 | 字号@1080p | 字号@1440p | 字号@2160p |
| --- | --- | --- | --- | --- | --- |
| **D1 展示标题** | 开场、章节定场、结论落锤 | 2.53 × | 96 px | 128 px | 192 px |
| **D2 标题** | 卡片主标题 | 1.68 × | 64 px | 85 px | 128 px |
| **T 正文** | 卡片正文、说明 | 1.00 × | 38 px | 51 px | 76 px |
| **L 标签** | 图例、轴名、字段名 | 0.74 × | 28 px | 37 px | 56 px |
| **M 微标签** | 编号、单位、credit、英文眉题 | 0.58 × | 22 px | 29 px | 44 px |

相邻两级的实际倍数是 **1.50 / 1.68 / 1.36 / 1.27**。全部 ≥ 1.27，保证层级一眼可辨；最上一级拉到 1.5—1.68，是因为它要压住整个画面。这是一条 **1.3—1.7 倍阶梯**，符合排版通行做法。五级里最小一级的绝对下限由字幕标准兜住：22 px 在 1080p 上是画面高度的 2.04%，低于 BBC 横屏字幕 7% 行高的一半，所以它**只能承载非关键信息**——这是设计的约束，不是可以放宽的地方。

### 2.2 行距

行距随字号反向变化：字越大，行距相对越紧。

| 级别 | lineHeight | 依据 |
| --- | --- | --- |
| D1 展示标题 | **0.94 — 1.00** | B/D。现有主题用 0.96 |
| D2 标题 | **1.00 — 1.08** | B/D。现有主题用 1.02 |
| T 正文 | **1.35 — 1.45** | B/D。现有主题用 1.38 |
| L 标签 | **1.25 — 1.35，单行时 1.0** | D |
| M 微标签 | **1.0**（单行） | D |

前提：字体必须有真实的字面留白。思源黑体的字面在字框中央且四周有空白，`1.35` 的行距足以避免中文上下相碰。

**未找到可靠依据**：中文视频画面的官方行距标准。clreq 6.4 只定义了「字型大小 = 文字外框的尺寸」，没有给出行高建议值。上面是排版通行做法（D 级）。

### 2.3 字距

| 场景 | letterSpacing | 依据 |
| --- | --- | --- |
| D1 展示标题（中文） | **-0.035em** | D。现有主题值，中文展示字号可以收紧到这个量 |
| D2 标题（中文） | **-0.025em** | D。现有主题值 |
| T 正文（中文） | **0** | A。clreq 6.3.1「密排」：字符外框彼此紧贴是中文排版的默认 |
| L 标签（中文） | **0 — +0.02em** | D |
| M 微标签（拉丁全大写） | **+0.18em — +0.22em** | D。现有主题用 0.2em |
| 拉丁正文 | 按字体默认 | A。clreq 6.3.3：横排西文使用比例字体 |

两条来自官方规范的约束：

- **正文级中文不要负字距。** clreq 6.3.1 明确中文默认是「密排」（字框紧贴）；「紧排」（字框部分重叠）在规范里的用途是「杂志标题及广告文案字数较多，为使其排列于一行，或为求特殊表现」，并明确说这条「不应用于书籍标题与内文的排列上」。所以负字距只给 D1/D2 展示级，正文保持 0。
- **中西文混排用 ¼ em 空隙。** clreq 6.3.3：横排时汉字与西文字母、数字之间使用**不多于¼个汉字宽**的字距或空白；但西文出现在**行首或行尾时不加**；中文点号前后、开始夹注符号之后、结束夹注符号之前也不加。

### 2.4 中文字体与拉丁字体混排

**第一件事：确认字体真的有你要的字重。**

思源黑体官方一共 **7 个字重**：ExtraLight、Light、Normal、Regular、Medium、Bold、Heavy。Adobe 官方 ReadMe 记录 ExtraLight 的 OS/2 `usWeightClass` 为 **250**（Thin 为 100）。Google Fonts 的 Noto Sans SC 是可变形字体，`wght` 轴 **100—900**。

在本机实测（决定代码里能不能用）：

```text
/Users/a1/Library/Fonts/                       ← 用户级，可用
  NotoSansCJKsc-Thin.otf        （100）
  NotoSansCJKsc-Light.otf       （300）
  NotoSansCJKsc-DemiLight.otf   （350）
  NotoSansCJKsc-Regular.otf     （400）
  NotoSansCJKsc-Medium.otf      （500）
  NotoSansCJKsc-Bold.otf        （700）
  NotoSansCJKsc-Black.otf       （900）   ← 真实 900 存在
```

- **本机没有 `Source Han Sans CN VF`。** 当前 `theme.ts` 的 `display` 字体栈里它排在 `Noto Sans CJK SC` 之后，实际不会命中。
- **苹方 PingFang SC 本机只有 6 个字重**：Ultralight、Thin、Light、Regular、Medium、Semibold（`fc-list` 实测）。**没有 700 以上的字重**。
- 推论：当字体栈落到苹方而代码要求 `fontWeight: 900` 时，得到的是浏览器合成加粗（假粗体），笔画会糊、字面会变形。这正是「看起来不专业」的一个具体成因。

**混排的四条可执行规则：**

1. **中文与拉丁分工，不让一种字体承担全部。** 中文主用真实存在的中文字重；拉丁用另一支几何黑体做展示、用窄体做数字。当前主题的分工（display / body / number / micro 四支字体栈）方向正确。
2. **不要把中文压成英文窄体。** 中文方格字被横向压缩后笔画粗细会不均匀。
3. **字号补偿（D 级）。** 同一 font-size 下，拉丁的小写字母视觉高度（x-height）通常低于中文方块字的字面高度，混排时英文看起来偏小。行业做法是把拉丁字号设为同级中文的 **1.05—1.10 倍**。**未找到公开规范依据**，这是观察到的做法。
4. **混排间距用（1.3）的 ¼ em，不要用全角空格。** clreq 6.3.3 的 Note 明确：也可以用西文词间空格 `U+0020`，但其宽度随字体变化，不可控。用可调 letter-spacing 或 `margin` 显式给 ¼ em 更稳。

### 2.5 数字

- **表格、图表、任何会变化的数字启用等宽数字**（`font-variant-numeric: tabular-nums`）。当前主题的 `number` 样式已经这样做了。
- 数字搭配窄体（Roboto Condensed / DIN Condensed 一类）是行业做法，**未找到规范依据**；但「数字与类别名不能共用同一字宽和字距」这个判断成立，因为等宽数字在中文正文黑体里会留下不均匀的空隙。
- 官方定义出处：OpenType `tnum` 特性与 CSS `font-variant-numeric` 的 `tabular-nums` 关键字，见 [MDN font-variant-numeric](https://developer.mozilla.org/en-US/docs/Web/CSS/font-variant-numeric)。

## 3. 色彩

### 3.1 对比度门槛

| 对象 | 门槛 | 出处 | 可靠性 |
| --- | --- | --- | --- |
| 正文文字（< 18pt 非粗体 / < 14pt 粗体） | **≥ 4.5:1** | WCAG 2.2 SC 1.4.3（AA） | A |
| 大号文字（≥ 18pt 非粗体 / ≥ 14pt 粗体） | **≥ 3:1** | WCAG 2.2 SC 1.4.3 例外条款 | A |
| 增强对比度 | **≥ 7:1** | WCAG 2.2 SC 1.4.6（AAA） | A |
| 非文本（图标、图形、需要理解的图形元素、控件边界与状态） | **≥ 3:1** | WCAG 2.2 SC 1.4.11（AA） | A |

**大号文字的判定在中文上怎么算**：WCAG 的正式定义是「at least 18 point or 14 point bold **or font size that would yield equivalent size for Chinese, Japanese and Korean (CJK) fonts**」，并且给了换算 `1pt = 1.333px`，即 `18pt ≈ 24px`、`14pt ≈ 18.5px`。

对视频的换算：在 1080p 画面按 3 米观看距离下，24 px 属于小字。因此**不要指望靠「字够大」把门槛降到 3:1**——对叠在录屏上的卡片，正文一律按 **4.5:1** 执行，只有 D1/D2 展示级才可以按 3:1。

计算公式（WCAG 原文）：`contrast ratio = (L1 + 0.05) / (L2 + 0.05)`，其中 L 是相对亮度，`L = 0.2126R + 0.7152G + 0.0722B`，分量需先做 sRGB 线性化。**不要四舍五入**：4.499:1 不满足 4.5:1。

**关于 APCA**：APCA（Accessible Perceptual Contrast Algorithm）是 WCAG 3 的候选算法，**目前仍是草案，不是标准**。它用 `Lc` 值（0—±106）表达轻重对比，官方公开的用途档位是：`Lc 90` 为成栏正文首选（≥14px/400）、`Lc 75` 为成栏正文最低（≥18px/400）、`Lc 60` 为非成栏但要读的正文最低（24px/400 或 16px/700）、`Lc 45` 为大号粗体标题最低（36px/400 或 24px/700）。APCA 的正当用途是**检查深色模式下的实际观感**——它的作者明确指出 WCAG 2 的比值「在近黑背景上会严重高估对比度」。本文件的做法：**用 WCAG 2.2 做通过与否的判定，用 APCA 的感觉做微调**，不改判定标准。

### 3.2 强调色用几个、用在哪里

**规则：一个画面最多 1 个强调色在「表达」，最多 3 个语义色在「承载含义」。**

- **表达用（1 个）**：当前观点、当前结论、当前节点。承担「现在看这里」。
- **语义用（3 个）**：`info` / `warning` / `danger`。只在信息本身有对应语义时出现，不做装饰。
- **禁止把强调色当分类色用。** 给 5 个并列条目各配一个颜色，是把颜色当编号；颜色一多，就没有任何一个是强调。

这条规则的可靠性是 **D 级（从业者共识/观察）**。Vox 风格被第三方拆解出的特征之一是「flat design and limited palette」，可以佐证方向，但**未找到任何官方规范写着「一屏一个强调色」**。

### 3.3 避免「一眼廉价」的配色

这一节的每条都有 A/B 级依据。

**1. 深底上不要用纯白正文。**

Google 的 Material 深色主题官方教程给出明确的数值与原因：

| 角色 | 值 |
| --- | --- |
| 最底层表面 | `#121212` |
| 高强调文字 | `#FFFFFF` @ **87%** 不透明度 |
| 中强调文字 | `#FFFFFF` @ **60%** |
| 失效文字 | `#FFFFFF` @ **38%** |
| 抬升表面（overlay） | `#FFFFFF` @ **2% / 12%** 叠加在 `#121212` 上 |

官方给出的理由是：`#FFFFFF` 是亮色，在深底上会「visually vibrate」（视觉振动），而且纯白文字的光会在深底上「bleed or blur」（渗出或发虚），损害可读性。

**不要把 Material 的 87% 直接抄成「正文用 87% 白」。** Material 的 87% 是给 App 界面文字的，界面文字通常比视频叠层文字大、且距离观看者近。视频叠层文字更小、观看距离更远，需要更高的实际对比度。本文件的取值（见第 4 节实测）是 **正文 92%—100% 白**，仅在 D1 展示级才降到 87%—90%。

**2. 深底上用「抬升」而不是「投影」表达层级。**

深色主题下阴影几乎不可见，Material 的解法是用更亮的 overlay 表示更高的层级。这对你的卡片是直接的替代方案：**卡片不用靠阴影浮起来，靠比背景亮一档的表面色区分。**

**3. 线条和边界必须达到 3:1。**

这是当前主题最容易出问题的地方。经实测，四个深色主题的 `line` 色对背景的对比度是：

| 主题 | `line` 色 | 对 background | 对 surface | 3:1 判定 |
| --- | --- | --- | --- | --- |
| `editorial-dark` | `#303744` | **1.65 : 1** | 1.57 : 1 | 不通过 |
| `momentum` | `#41464B` | **1.98 : 1** | 1.79 : 1 | 不通过 |
| `tech` | `#315A51` | **2.47 : 1** | 2.21 : 1 | 不通过 |
| `warning` | `#684135` | **2.13 : 1** | 1.93 : 1 | 不通过 |

如果一个 1px 的边框、一条分隔线或一个坐标轴**承载了理解信息**（区分两个区域、表示刻度、标出边界），它就落入 SC 1.4.11 的范围，需要 3:1。这不是「好不好看」的问题，是硬门槛。

**4. 半透明面板的对比度不可预测。**

`surface: "rgba(15, 18, 24, 0.90)"` 这类值的实际对比度取决于底画内容。底画是浅色录屏时，叠加后的表面会变亮，白字对比度可能从 17:1 掉到 4:1 以下。可执行的做法有两条：

- 面板用**接近不透明**（≥ 96%）或直接不透明；
- 只做局部不透明的**底衬**（文字后面贴一块实色渐变），而不是整块半透明面板。

## 4. 边框、圆角、阴影、描边

### 4.1 什么时候该用

| 手段 | 该用的条件 | 数值 |
| --- | --- | --- |
| **卡片底色块** | 卡片叠在**信息密度高的底画**（录屏、截图、图表）上，需要把内容从背景里「摘」出来 | 表面色比背景亮一档；不透明度 ≥ 96% |
| **1px 边框** | 卡片底色与底画亮度接近（对比 < 3:1），需要一条明确的边界 | 边框色对相邻色 ≥ 3:1 |
| **圆角** | 容器类元素（卡片、面板、按钮、徽章） | 见 4.2 |
| **阴影** | 元素**真的浮在底画上方**（悬浮面板、弹层、提示条） | 见 4.3 |
| **文字描边** | 只有字幕需要 | 黑色描边，宽度 **4**，不透明度 100（依据：国家标准 6.3.4） |

### 4.2 圆角

**Material Design 3 的官方形阶**（`none(0)` / `extraSmall(4)` / `small(8)` / `medium(12)` / `large(16)` / `extraLarge(28)` / `full(9999)`，单位 dp）：

| 元素类型 | dp | 1080p（×1） | 1440p（×1.333） | 2160p（×2） |
| --- | --- | --- | --- | --- |
| 芯片、徽章、输入框 | 4 | 4 px | 5 px | 8 px |
| 按钮、小卡片 | 8 | 8 px | 11 px | 16 px |
| **卡片、面板**（最常用） | **12** | **12 px** | **16 px** | **24 px** |
| 大卡片、重点内容块 | 16 | 16 px | 21 px | 32 px |
| 主视觉卡、对话框 | 28 | 28 px | 37 px | 56 px |
| 胶囊 / 圆形 | 9999 | 高度的一半 | 同 | 同 |

换算方式：以 1080p 为 1 dp = 1 px 的基准，1440p 乘 1.333，2160p 乘 2。（若把 1080p 当作「2 倍图」处理，即按 CSS 尺寸乘以 2 输出，则所有值翻倍；两种口径任选一种，但同一支视频必须统一。）

M3 Expressive 更新把 large 提到 20、extraLarge 提到 32；旧值 16 / 28 仍在使用。**同一支视频里只用一档卡片圆角**，不要把 8、12、16 混着用——混用会让观者读不出层级差异，只觉得「随便设的」。

**小尺寸元素（图表标记、轴上的点、小于 24px 的方块）用 4 或 0。** 12dp 的圆角套在 16px 的方块上等于把它变成药丸，形状本身失去意义。

### 4.3 阴影

深色主题下阴影基本不可见（Material 官方说明：背景太暗以致无法可靠地用暗色阴影表达层级）。所以：

- **深色主题：优先用「表面亮度抬升」表达层级，不用阴影。**
- **浅色主题或必须表现物理层叠时**才用阴影。

**未找到可靠依据**：视频叠加层专用的阴影参数（模糊半径、偏移、不透明度）标准。上面是 Material 的官方立场（B 级）加推断。

### 4.4 描边

| 场景 | 做法 |
| --- | --- |
| 字幕 | 白字 `#FFFFFF` + 黑描边 `#000000`，宽度 **4**，不透明度 100%（国家标准 6.3.4） |
| 叠在不可预测底画上的浮层文字 | 同字幕做法 |
| 卡片标题、正文 | **不要描边。** 有底衬就不需要描边；既加底衬又加描边是双保险，会把字挤瘦 |
| 图形轮廓 | 仅在需要区分同色相邻图形时加，且必须达到 3:1 |

### 4.5 新手常见错误

用户明确要求在文档里记录这些禁止/错误项，故本节采用「错误表现 → 为什么错 → 正确做法」的写法。

**错误 1：给每一块文字都套一个圆角矩形色块。**

表现：一个画面里 6 个条目，每个都是一张圆角卡片，颜色还不一样。

为什么错：卡片的作用是**建立边界**。当所有东西都有边界时，边界就不再传递「这是一组」的信息，只留下视觉噪音。而且卡片会遮住底画——你的底画是录屏，本身就承载内容，遮得越多，观众越难把讲解和屏幕操作对应起来。

正确做法：一个画面里卡片数量 **≤ 3**。同一层级的多个并列条目用**一个**容器装，条目内部用 `line` 分隔或纯间距分隔，不各自套卡。

**错误 2：圆角值随内容长度变化。**

表现：长文本卡片圆角 16，短文本卡片圆角 8。

为什么错：圆角是**层级信号**（M3 的形状系统明确把圆角当作表达层级和归属的手段）。随尺寸变化就让这个信号失效了。

正确做法：按 4.2 的元素类型定档，同类型同值。

**错误 3：深色主题用大而软的投影「让卡片浮起来」。**

为什么错：深色底上投影几乎不可见，只能看到一层脏灰晕。Material 的官方立场是深色主题改用亮度 overlay。

正确做法：`surface` 色比 `background` 亮一档。实测差距参考：`#090B0F` → `#0F1218`（editorial-dark）、`#101112` → `#1B1D1F`（momentum）、`#07110F` → `#0F1E1B`（tech）。

**错误 4：同时给文字加底色块、描边和阴影。**

为什么错：三重保险会压缩字面（描边向内吃），并且让文字在视觉上变细、对比度反而下降（WCAG 文档专门提到抗锯齿和细字体在名义对比度合格时实际可能更淡）。

正确做法：**一条通道解决一个问题。** 背景不可预测 → 用底衬；底衬对比不足 → 加边框；要浮起来 → 抬亮表面色。三者按需取其一。

**错误 5：给并列分类各配一个颜色。**

为什么错：颜色变成编号，强调失效。见 3.2。

**错误 6：所有元素用同一种淡入。**

这条在本项目的 `动画效果库.md` 里已经写明是禁忌，此处补充量化替代方案：不同语义角色用不同入场（见第 7 节）。

## 5. 间距与留白

### 5.1 安全边距

对齐三套 A 级依据后的取值：

| 对象 | 内缩 | 1080p | 1440p | 2160p | 依据 |
| --- | --- | --- | --- | --- | --- |
| 全部图形、卡片的**硬边界** | **5%** | 96 水平 / 54 垂直 | 128 / 72 | 192 / 108 | EBU R95 Graphics Safe Area |
| 关键动作、被指对象 | 3.5% | 67 水平 / 38 垂直 | 90 / 50 | 134 / 76 | EBU R95 Action Safe Area |
| 片头片尾字幕 | 10%（不超出 80% 区域） | — | — | — | GY/T 357—2024 9.1.1 |
| 右侧摄像头小窗避让 | 小窗宽 + 5% 边距 | — | — | — | 本项目约定 |

对 16:9 的 1080p（1920×1080）：5% 的水平内缩是 **96 px**，垂直内缩是 **54 px**。

**注意水平与垂直的百分比不同。** EBU R95 的 5% 是「画面高度/宽度的 5%」，在 16:9 上得到的是非对称的像素值。这是常被忽略的细节。

### 5.2 字幕区

- 字幕区高度 = 画面高度的 **10%**（GY/T 357—2024 9.1.2）。1080p 上是 **108 px**。
- 字幕区**默认留空**，任何卡片、标注、图形都不得进入。
- 单行字幕行高 = 画面高度的 **7%—8%**，1080p 上是 **75—86 px**（BBC 9.2.1）。
- 字身高度 = 画面高度的 5% ± 1%，1080p 上是 **54 px ± 11 px**（GY/T 357—2024 9.3.1）。

字幕区留空这条同时解决两个问题：字幕永不被遮挡，卡片信息量被强制约束。

### 5.3 元素间距比例

基础网格 **4 px**。间距只用这几个值：

| 关系 | 间距 | 1080p | 比例语义 |
| --- | --- | --- | --- |
| 同组内相邻元素（图标与文字、标签与数值） | 1 倍 | **8 px** | 紧耦合 |
| 同一卡片内相邻段（标题与正文） | 2 倍 | **16 px** | 同组 |
| 卡片内边距（padding） | 3—4 倍 | **24—32 px** | 容器呼吸 |
| 相邻卡片之间 | 4 倍 | **32 px** | 并列关系 |
| 卡片与底画边缘（在安全边距之内） | 8—12 倍 | **64—96 px** | 主次分隔 |

**核心比例关系**：`卡片内边距 : 卡片间距 = 1 : 1 到 1 : 1.33`。这个比例决定了「哪些东西属于同一组」能不能被看出来——组内距 < 组间距，分组才成立。这是格式塔接近性原则的直接应用，属 D 级但可靠。

**留白下限**：一组内容如果占据了超过 **可用宽度的 80%** 或 **可用高度的 80%**，就要考虑拆分或删减。留白不是浪费，是让眼睛知道该停在哪里。

### 5.4 一行放多少个中文字

由每行字数上限反推：

- 正文 38 px 时，若可用宽度为 1920 − 2×96 = 1728 px，理论上可放 45 个中文字。**但不要把一行排满。**
- 参考 Netflix 的中文硬限（23 字/行）和国标（每屏 ≤ 14 字），**卡片正文单行不超过 20 个中文字**，超过就手动断行。
- 断行必须断在**完整意群**上。clreq 6.1.1 定义了行首行尾禁则：标点不能出现在行首等规则。Remotion 里不要依赖浏览器自动断行处理中文，手工在语义边界插入换行。

## 6. 动画与语音对齐

### 6.1 入场时机的量化规则

| 规则 | 数值 | 依据 |
| --- | --- | --- |
| 元素入场对齐到**它对应的那个词的起音** | 误差 **±1—2 帧**（1080p30 下 ±33—67 ms） | Netflix §1 是字幕的容差；卡片沿用同一量级 |
| 动画放在该词**之前**还是**之后** | 与该词**同时或之后 0—2 帧**开始 | D。manim 的 `lingering` 机制说明：需要「先讲再出现」时用保持动画占位，而不是提前出现 |
| 元素停留到下一次变化 | 不设固定值；下一个语义单元出现时才降权或替换 | D |
| 离场 | 优先整组降权/整场景转场，而不是逐个退场 | D。现有 `动画效果库.md` 已有此判断 |

### 6.2 时长与缓动

**Material Design 3 官方推荐的缓动—时长组合**（B 级）：

| 缓动 | 时长 | 过渡类型 |
| --- | --- | --- |
| Emphasized（强化） | **500 ms** | 在屏幕内开始并结束 |
| Emphasized decelerate（强化减速） | **400 ms** | 入场：从屏幕外进入 |
| Emphasized accelerate（强化加速） | **200 ms** | 退场：从屏幕内移出 |
| Standard（标准） | **300 ms** | 在屏幕内开始并结束 |
| Standard decelerate（标准减速） | **250 ms** | 入场：从屏幕外进入 |
| Standard accelerate（标准加速） | **200 ms** | 退场：从屏幕内移出 |

M3 的缓动特征是「起步干脆利落，收尾柔和舒缓」，为此 M3 的时长比 M2 略长，好让动画有时间自然停下。

**翻译到视频叠层**（D 级，由上面推导）：

| 动作 | 时长 | 类比 |
| --- | --- | --- |
| 卡片/文字入场（本来就在画面内出现） | **160—240 ms** | Standard decelerate 250 ms |
| 卡片/文字入场（从画面边缘滑入） | **240—400 ms** | Emphasized decelerate 400 ms |
| 强调（高亮扫过、脉冲、描边亮起） | **120—200 ms** | 短、准、少 |
| 元素逐个错峰（stagger） | 间隔 **60—100 ms** | D |
| 退场 | **200 ms** | Standard accelerate |
| 场景转场 | **500 ms** | Emphasized |

**硬规则：单个元素的入场动画不超过 400 ms。** 超过 400 ms 的入场动画会和口播抢时间——口播一个字大约 150—250 ms，动画比一个字还长，观众就会在「看字」和「看动画」之间被撕扯。

**缓动曲线**：入场用减速曲线（先快后慢），退场用加速曲线（先慢后快），画面内状态变化用先加速后减速的对称曲线。具体 cubic-bezier 数值请从 Material 官方 token 页取，本文件不复制可能过期的曲线常量。

### 6.3 逐字/逐词出现的节奏

**这个问题的公开方法论是本次调研里覆盖最弱的一块。诚实说明如下。**

**有依据的部分：**

1. **manim 的做法可以作为参照。** 3Blue1Brown 使用的 manim 里，每个动画有 `run_time` 参数，默认 **1 秒**，默认缓动 `smooth`；需要「停留」时用 `lingering`。也就是说**每个动画的时长是被显式指定的参数，不是自然发生的**。这条是 C 级（官方文档）。
2. **字幕与语音的对齐规则可以复用。** Netflix §1 的规则是：入场时间落在语音首帧上，容差 1—2 帧；出点比对话结束晚至少 0.5 秒。BBC §4.1：按 160—180 wpm 折算，每个词至少留 **0.3 秒**。
3. **逐词出现的间隔下限可以由上面的数字推出**：英文每词 ≥ 0.3 秒（BBC）。中文没有对应的官方数字，按国标 3—5 秒/14 字折算，每字约 **0.21—0.36 秒**，与英文同量级。

**没有依据、必须标明的部分：**

- **「动画应该在语音开始前还是结束后出现」——未找到可靠的公开研究或规范。** 现有做法（「与词同步或稍后」）是从字幕对齐规则外推的，不是被验证过的结论。
- **逐词高亮（karaoke 式）对理解或记忆是否有正面效果——未找到可靠依据。** 这类动效在这些作品里并不常见。
- **中文逐字出现的具体节奏——未找到公开方法论。**

**因此本文件对逐词的立场是保守的：**

> 逐字/逐词出现**只用于「文字本身就是内容」的场合**（金句、定义、关键结论）。其余场合用整块出现的 Fade + Slide（160—240 ms）。
>
> 逐词出现时，**一个词的显示时长不得短于它对应的语音时长**，宁可与语音完全同起同落，也不要为了「动效好看」而加快或放慢。

**已确认无依据的说法，不要写进制作规范：**

- 「每个字 0.1 秒逐个出现」——数字来源不明。
- 「打字机效果更有科技感」——`Type On` 在本项目 `动画效果库.md` 里已限定为「字段填写、搜索框、控制台文字」等有语义的场合，这是正确判断，但没有外部依据。

## 7. 可直接采用的默认值表

以下数值可直接写入 `theme.ts` / `typography` 常量。

**换算口径（三张表统一用同一套，不要混）：**

```text
1080p (1920×1080)  = 基准，1 dp = 1 px = 1 字号单位
1440p (2560×1440)  = 基准 × 1.333
2160p (3840×2160)  = 基准 × 2
```

含义：本表的 1080p 字号 38 对应 Remotion composition 高度 1080 时的 `fontSize: 38`。同一个 composition 若改为 1440 或 2160 高，按上表乘系数。这与「1080p 输出到 4K 屏幕被放大」是两回事——后者不需要改任何数值。

### 7.1 字号层级

| 级别 | 用途 | 1080p | 1440p | 2160p | 字重 | 行距 | 字距 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| D1 展示标题 | 开场、章节定场、结论落锤 | 96 | 128 | 192 | 900 | 0.96 | −0.035em（中文） |
| D2 标题 | 卡片主标题 | 64 | 85 | 128 | 700 | 1.02 | −0.025em（中文） |
| T 正文 | 卡片正文、说明 | 38 | 51 | 76 | 500 | 1.38 | 0（中文） |
| L 标签 | 图例、轴名、字段名 | 28 | 37 | 56 | 500 | 1.30 | 0 — +0.02em |
| M 微标签 | 编号、单位、英文眉题 | 22 | 29 | 44 | 800（拉丁全大写） | 1.0 | +0.20em（拉丁） |
| NUM 数字 | 数据、指标 | 按所处层级 | 同 | 同 | 700（窄体） | 0.92 | −0.02em + `tabular-nums` |

**字体栈**（本机实测可用的顺序）：

```text
中文展示 / 正文： "Noto Sans CJK SC", "Source Han Sans CN VF", "PingFang SC", sans-serif
拉丁展示：       "Montserrat", "Arial Black", sans-serif
拉丁数字：       "Roboto Condensed", "DIN Condensed", "DIN Alternate", sans-serif
拉丁微标签：     "Montserrat", "Avenir Next", "Helvetica Neue", sans-serif
```

**字重可用性检查（改字体前必做）**：本机 `Noto Sans CJK SC` 有 100/300/350/400/500/700/900 七个真实字重；`PingFang SC` 只有 Ultralight/Thin/Light/Regular/Medium/Semibold 六个，**没有 700 以上**。要求 900 而字体栈落到苹方，会得到合成假粗体。

### 7.2 对比度

| 用途 | 门槛 | 说明 |
| --- | --- | --- |
| 正文文字 | **≥ 4.5:1** | 硬门槛，不四舍五入 |
| D1 / D2 文字 | ≥ 3:1 | 允许，但仅在字号确实达到大号文字时 |
| 图标、图形、线条、卡片边界 | **≥ 3:1** | 承载理解信息时适用 |
| 推荐目标（非门槛） | 文字 **≥ 7:1**，图形 ≥ 3.5:1 | 深底视频的观感需要高于门槛 |
| 纯白正文 | **不用 `#FFFFFF` 大写正文** | 深底上会振动、发虚 |
| 高强调文字 | `#FFFFFF` @ 92%—100% | 视频叠层取比 Material 的 87% 更高的值 |
| 中强调文字 | 实测值即可（现有 `muted` 全部 7.6—11.6:1，无需下调） | — |
| 线条 | 见 3.4 的建议新值 | 现有四个深色主题的 `line` 全部不达标 |

### 7.3 圆角

| 元素 | dp | 1080p | 1440p | 2160p |
| --- | --- | --- | --- | --- |
| 小元素（芯片、徽章、输入框） | 4 | 4 | 5 | 8 |
| 按钮、小卡片 | 8 | 8 | 11 | 16 |
| **卡片、面板（默认）** | **12** | **12** | **16** | **24** |
| 大卡片、重点块 | 16 | 16 | 21 | 32 |
| 主视觉卡、对话框 | 28 | 28 | 37 | 56 |
| 图表标记、≤24px 的方块 | 0 或 4 | 0—4 | 0—5 | 0—8 |
| 胶囊 | 高度/2 | — | — | — |

同一支视频只用一档卡片圆角。

### 7.4 间距

| 用途 | 1080p | 1440p | 2160p |
| --- | --- | --- | --- |
| 图形硬边界（5%） | 96 水平 / 54 垂直 | 128 / 72 | 192 / 108 |
| 关键动作边界（3.5%） | 67 水平 / 38 垂直 | 90 / 50 | 134 / 76 |
| 字幕区高度（10%） | 108 | 144 | 216 |
| 字幕行高（7.5%） | 81 | 108 | 162 |
| 字幕字身（5% ± 1%） | 54 ± 11 | 72 ± 14 | 108 ± 22 |
| 同组内元素 | 8 | 12 | 16 |
| 同卡片内相邻段 | 16 | 20 | 32 |
| 卡片内边距 | 24—32 | 32—44 | 48—64 |
| 相邻卡片 | 32 | 44 | 64 |
| 卡片与画面边缘 | 64—96 | 84—128 | 128—192 |

**百分比类数值按精确比例换算**（×1.333 / ×2），**网格类间距按 4 px 取整**。基础网格 4 px。不用 5、6、7、10、13 这类非网格值。

### 7.5 强调色用法

| 角色 | 数量 | 用在哪里 | 不用在哪里 |
| --- | --- | --- | --- |
| 表达强调 | **1 个/画面** | 当前观点、当前结论、当前节点、口播正在讲的那个词 | 并列分类、装饰性色块、背景渐变 |
| `info` | 1 | 中性信息、链接感元素、技术过程 | 与表达强调混用 |
| `warning` | 1 | 风险、注意事项、需要留意的条件 | 强调「重要」（重要用表达强调） |
| `danger` | 1 | 错误、失败、禁止 | 情绪化用色 |
| `success` | 1 | 通过、完成、正确路径 | 与 danger 同时大面积出现 |

**同时出现在一个画面的语义色 ≤ 3 个。** 超过就是配色失控。

### 7.6 动效

| 动作 | 时长 | 入场时机 |
| --- | --- | --- |
| 卡片/文字出现（画面内） | 160—240 ms | 对应词的起音，误差 ≤ 2 帧 |
| 卡片/文字滑入（画面外） | 240—400 ms | 同上 |
| 强调（高亮、脉冲） | 120—200 ms | 讲到该词时 |
| 逐元素错峰间隔 | 60—100 ms | 按语义顺序 |
| 退场 | 200 ms | — |
| 场景转场 | 500 ms | — |
| **单元素入场上限** | **400 ms** | 超过就抢口播 |
| 逐词出现 | 每词 ≥ 其对应该词的语音时长 | 只用于金句/定义/结论 |

### 7.7 一屏内容量上限

| 项 | 上限 |
| --- | --- |
| 需要被读的中文字总数 | **30 字** |
| 文字层级数 | **3 级** |
| 卡片数量 | **3 张** |
| 同时出现的语义色 | **3 个** |
| 正文单行中文字数 | **20 字** |
| 字幕单行 | 中文 23 字（硬限）/ 16 字（Originals 标准） |
| 字幕单屏 | 14 字、2 行 |
| 字幕停留 | 3—5 秒 |

## 8. 一页检查清单

出片前对每一屏逐条勾：

```text
[ ] 需要被读的中文字 ≤ 30
[ ] 文字层级 ≤ 3 级，且字号差距 ≥ 1.3 倍
[ ] 正文对比度 ≥ 4.5:1，线条/图形 ≥ 3:1，均未四舍五入
[ ] 没有用 #FFFFFF 做正文
[ ] 卡片数量 ≤ 3；同层级并列条目共用一个容器
[ ] 同一屏只用一档卡片圆角
[ ] 深色主题没有靠阴影表达层级（用表面亮度差）
[ ] 文字没有同时加底衬 + 描边 + 阴影
[ ] 一个画面的强调色只有 1 个，语义色 ≤ 3 个
[ ] 所有图形在 5% 安全边距内；字幕区（底部 10%）留空
[ ] 正文单行 ≤ 20 个中文字，断行在完整意群上
[ ] 中西文之间有 ¼ em 空隙（行首行尾除外，点号旁不加）
[ ] 所有中文字重在本机字体里真实存在（无合成加粗）
[ ] 单元素入场 ≤ 400 ms；动画起点对齐语音首帧（误差 ≤ 2 帧）
[ ] 逐词出现只用在金句/定义/结论，且每词停留 ≥ 语音时长
[ ] 间距全部落在 4 px 网格上
```

| --- | --- |
| 「一屏只用 1 个强调色」 | 未找到官方规范。方向有第三方拆解佐证（Vox 有限调色板），本文件标为 D 级 |

| 视频叠加层的阴影参数标准 | 未找到。本文件的立场由 Material「深色主题不用阴影」推导 |
| 「动画应在语音开始前还是结束后出现」 | 未找到可靠研究或规范 |
| 逐词高亮对理解/记忆的效果 | 未找到可靠依据 |
