# CapMotion 双端构建与发布

## 交付边界

桌面包提供 CapMotion、Cap CLI、导出器和所需媒体库；Node、FFmpeg 命令行、Remotion workspace、项目 Skill 和 HTML 审稿生成器通过仓库与开发环境使用。安装桌面包不等于已安装整套 Agent 工具链。桌面版共用应用标识 `com.laohu.capmotion`、版本和中英更新日志；个人工程、凭据和预设保存在各自系统用户目录，不打入公共安装包。

当前发布目标为 macOS Apple Silicon 和 Windows x64。macOS Intel、Windows ARM 原生构建不在这两个资产的覆盖范围。跨机器使用既有工程时需要带齐工程媒体并重新定位外部路径；不能把历史记录里的 Mac 源时码或源媒体路径改成假想 Windows 路径。

## 历史功能检查矩阵

| 范围 | 两端共用能力 | Windows 处理与验证 |
| --- | --- | --- |
| 首次运行与中文界面 | 语言选择、持久设置、翻译字典、应用自己的更新日志 | 保留 Windows 的首次运行分支，不显示 macOS 专用录屏授权门；运行语言与权限状态测试 |
| 摄像头、麦克风权限 | 设备选择、错误与重试 | 增加 Windows 隐私设置按钮，打开 `ms-settings:privacy-webcam` / `ms-settings:privacy-microphone`；真实设备仍需实机验收 |
| 应用设置 | 通知、自定义工程存储、预设、CLI 管理 | 通知选项不再被 macOS 条件隐藏；Dock 选项仅在 Mac 显示；路径示例按系统显示 |
| 编辑器与字幕 | EDL revision、字幕双轨、轨级位置、预设增量保存、样式 | 同一套预设、字幕轨、位置和存储测试在 Windows 运行；不另存一套个人样式默认值 |
| 鼠标与快捷键 | 平移、缩放、多轨浏览、画布调整 | Windows 普通滚轮平移、Ctrl + 滚轮缩放、Shift + 滚轮上下浏览轨道；Mac 保留 Command + 滚轮上下浏览 |
| Agent CLI | 工程锁、原子写、revision 与回执 | Windows 使用 cap.cmd 和随包 cap-cli.exe；已有 shim 路径测试与安装后真实 CLI 启动检查 |
| Remotion | 官方 JS 入口、同一渲染质量与输出契约 | 通过 Node 直接传递参数，不经 .cmd；中文、空格、引号、& 和 JSON 参数端到端进程测试 |
| ASR 入口 | 按录制段读取麦克风，保留原始词级时间 | 音频抽取使用 Node/FFmpeg，删除 Bash 与 BSD stat 依赖；不调用付费 API 验证安装 |
| HTML 审稿 | 疑难、源/成片时码、字幕、动画跨段、参考图、反馈草案 | 离线 HTML 不依赖 macOS；与 EDL/方案版本绑定，浏览器反馈不自动变成开工批准 |
| 日志与更新 | 独立应用标识、CapMotion GitHub Releases | Windows 日志使用 LocalAppData 下 com.laohu.capmotion，不再写入上游 Cap 目录；两端只提示打开下载页 |
| 打包 | 单一版本与双语日志校验、Tauri 界面 | 专用 NSIS，含英文与简体中文、用户级安装；不要求 GPUI 或上游私有发布凭据 |

Windows 隐私入口依据 Microsoft 的 [Windows 设置 URI 文档](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-settings)。Windows 桌面设备访问不等同于 macOS 的逐应用授权状态，不能把“无需本工具请求”宣称为设备已授权。

## 构建与保存位置

本机所有发布安装包、下载产物、编译临时文件与报告放在当前工作盘的 `target/capmotion-release/`。该目录被 Git 忽略。`scripts/build-cap-local.sh` 默认将 TMPDIR 放在同盘；可用 CAP_BUILD_TMPDIR 显式指定其他构建盘，不默认占用系统盘 Downloads 或 /tmp。

Mac 打包并保留当前运行的独立版（在仓库根目录执行）：

```bash
CAP_LOCAL_PACKAGE_OUTPUT="$PWD/target/capmotion-release/CapMotion-0.1.3-macos-arm64.zip" bash scripts/build-cap-local.sh
```

Mac 脚本检查已有持久签名证书和已安装版本的身份兼容性；归档模式只生成文件，不关闭、覆盖或重新授权正在使用的应用。当前为持久自签名社区包，未做 Apple 公证。

Windows 使用 PowerShell 7、Node 22、项目锁定的 pnpm、Rust 1.88 与 Visual Studio 2022 C++ 工具链：

```powershell
pnpm install --frozen-lockfile
./scripts/build-cap-windows.ps1
./scripts/verify-cap-windows.ps1
```

Windows 依赖准备会下载 FFmpeg 7.1、DirectX Shader Compiler、ONNX Runtime 和字幕字体。Agent 调用独立 FFmpeg 时需把命令行程序加入 PATH，或分别设置 FFMPEG_BIN / FFPROBE_BIN。PowerShell 多行续行用反引号，不能直接使用 Bash 的反斜杠。

云端通过 `.github/workflows/capmotion-windows.yml` 构建，在含中文与空格的目录静默安装，检查主程序、三个 sidecar、媒体 DLL、版本、CLI 与桌面启动。报告与安装包保存在同一 CI artifact。没有配置 Authenticode 证书时报告明确标记未签名，不伪造签名或隐藏系统提示。

## 发布门槛与限制

1. 更新 `tauri.local.conf.json` 的版本；同一改动失败重试不重复加号。先写同版本 `capmotion-changelog.json` 中英文记录。
2. 运行项目工具、字幕/预设/语言/交互和原生工程接口回归。两端必须针对将要发布的源码构建。
3. Mac 检查归档、bundle 版本、签名、侧载工具与资源；Windows 检查安装、DLL、CLI 和应用启动。失败包不上传公开 Release。
4. 真实摄像头、麦克风、GPU 录制、交互编辑和导出属于设备验收；云端安装冒烟测试不能替代它。发布说明如实区分已自动验证项与尚未覆盖的硬件场景。
5. 将确认的代码合入 main 并推送。GitHub 操作显式指定 `--repo LaohuAD/laohu-CapMotion`，避免 gh 自动选择上游 CapSoftware/Cap。
6. 从同一条中英更新日志生成 Release 正文，提供两端资产、SHA-256 与验证范围；多行正文用文件传入，禁止发布字面量反斜杠 n。
7. 第三方参考克隆、node_modules、target、凭据与源媒体不推 Git；项目规范、Skill、模板、实现和用户授权公开的文字记录随仓库同步。

## 本次改动的判断与回归

失败证据：历史发布只产出 Mac 包；公共通知设置受 Mac 条件控制；Windows 权限按钮为空实现；ASR 抽取调用 Bash 和 BSD stat；动画启动依赖平台 shim。最早失效点是发布与验证入口只有 Mac 路径，导致系统差异没有进入回归。

采用：以共用功能契约和 Windows 原生构建补齐缺口；保护现有字幕/预设/时间映射、Mac 持久签名、用户运行会话和渲染质量。未采用：重写两套 UI、搬移个人媒体、绑定某种动画风格、把官方 Skill 当成桌面二进制升级。

回退条件：现有 Mac 行为或数据兼容性回归、Windows 安装或必需工具不能启动时，停止发布并修复；不通过删掉已有功能使构建变绿。代码与确定性测试可保留（KEEP），真实设备体验在完成实机回归前保持 OBSERVE，不宣称已经全硬件验收。
