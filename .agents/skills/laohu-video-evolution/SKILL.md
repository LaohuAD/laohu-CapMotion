# 老胡画面讲解项目进化

**改规则先追根，动旧物先保真。** 项目进化不是把反馈抄进顶层文件，也不是把长 Skill 剪短；它要找到结果最早在哪里失准，把判断修到唯一负责人，并证明旧能力没有随整理一起消失。

## 触发与边界

只在老胡明确要求“沉淀、优化项目、修改 Skill、补充长期能力、重构调用链”时启动。当前作品怎么改，先由作品负责人修；没有长期复用价值的意见留在当前作品。未经明确授权，不提交或推送 GitHub，不修改其他项目。

开始前读 `AGENTS.md`、真实调用入口、目标 Skill、它按条件引用的 Reference、相关脚本与测试。涉及大幅改写或删减成熟文件时，必须从 Git 原文读取被替换版本，不能用记忆或已经压缩过的摘要代替。具体审计与迁移方法见 [四层能力进化与保真](references/四层能力进化与保真.md)。

## 先找最早失效点

沿真实链路回溯：用户输入 → 路由 → 主 Skill → 必要中间结果 → 下游 Skill/脚本 → 成品 → 验收。不要停在最后暴露问题的文件。

内部先写清：

```text
症状：成品哪里失败
触发范围：当前作品 / 稳定偏好 / 待验证经验 / 项目能力 / 事实修正
最早失效点：哪个负责人本应留下什么，却留下了什么
四层根因：灵魂 / 筋骨 / 血肉 / 表皮
假设：改什么以后，同构任务会发生什么可观察变化
保护项：旧能力、事实、接口、资产和例外中哪些不能变差
唯一权威：应该修改的最接近根因位置
回退条件：什么结果证明本次修改不成立
```

同一症状可能跨层，但只选一个最早根因；下游受影响处作为连带修改，不把四处都写成根因。

## 把四层编译进 Skill

四层是能力来源，不是固定章节名。每个 Skill 必须用自己的领域语言回答：

- 灵魂：本能力最终替观众或运行者改变什么；面对两个都合理的方向，如何取舍。
- 筋骨：从什么输入进入，产生哪些必要中间结果，怎样交接、失败和回收。
- 血肉：使用什么真实材料与专业技法，作用于谁，为什么有效，怎样开始、变化、收束，过量风险是什么。
- 表皮：哪些是失败即打回的硬规格，哪些要靠观看、对照和语境判断分寸。

若一个判断只出现在 `AGENTS.md`，却没有进入相关 Skill 的输入、选择、否决、中间结果或验收，它仍是摆设。若知识只存在 Reference，却没有触发条件与激活回执，它等于没有接上调用链。

## 修改顺序

1. 盘点旧能力：触发、输入、关键判断、动作、例外、失败分支、输出、调用者、被调用者和测试。
2. 建立能力去向：保留原位、迁移、合并、降级或删除；不能指出替代位置的内容不得删除。
3. 先修唯一主 Skill 与必要中间结果，再修 Reference 路由、下游契约和确定性脚本。
4. 原则只负责定向，机制解释因果，执行给出动作，验收决定返工；不把所有规则压成箴言，也不让解释取代原则。
5. 为真实失败建立行为回归。测试应证明路由、输入或决定发生变化，不只检查文件中出现“四层”“高质量”等词。
6. 用 `scripts/evolution-record.mjs` 校验进化记录，再分别报告结构、路由、行为和质量结论。

## 验收

- `STRUCTURE`：路径、frontmatter、JSON、schema、命令和确定性接口。
- `ROUTE`：从真实请求能否到唯一负责人，Reference 是否按条件可达。
- `BEHAVIOR`：代表任务是否改变了判断、候选、否决或中间结果。
- `QUALITY`：真实成品、独立同构任务或领域裁决是否证明更好。

结构通过不能宣布能力通过；同一执行者修改并自测时，行为最高标为 `OBSERVE`。质量没有真实作品或独立裁决时写 `UNKNOWN`，不拿脚本通过冒充审美提升。

回归必须同时覆盖：当前失败、至少一项旧能力、至少一个相邻任务。最后只做 `KEEP / OBSERVE / REVERT`；证据不足的做法先观察，不写成永久禁令。
