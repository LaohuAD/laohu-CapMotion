# 用户偏好

本文件记录用户在调试过程中表达出的长期偏好。

## 已知偏好

- 项目目录名称要有实际语义，不喜欢无意义缩写。
- 当前项目根目录就是项目本身，不需要再套一层包装目录。
- 顶层说明集中放在 `AGENTS.md`，不需要多个 `README / PROJECT / STATUS` 分散管理。
- 可以保留简短迭代记录，但不希望文档体系过度复杂。
- 画面要真正帮助理解，而不是把口播变成屏幕文字。
- 用户不想要 PPT 式静态画面或动态 PPT，想要口播驱动的 MG 动画讲解效果。
- 希望项目随着作品积累，越来越懂用户想要的画面、效果、细节和节奏。
- 画面不仅要展示口播已经讲到的内容，也要合理补充口播没有展开但有助于理解、进阶和行动的信息。
- 画面目标要向优秀自媒体讲解视频靠拢，有精美度、吸引力、细节和节奏感。
- 画面内容要随着 ASR / 口播推进逐步出现、连接、点亮、变化和收束，不能一口气全部呈现。
- 大页、流程图、关系图、控制台等完整画面需要足够停留时间，不能 3 秒闪过。
- 用户不喜欢画面只有少量文字和大面积空卡片；希望信息更丰富，但通过图解、标注、箭头和关系表达，而不是堆文字。
- 可以参考影视飓风这类成熟内容团队的讲解包装方向，但不能照搬风格。
- 用户每次提出作品修改指令、控制意见、审美判断、效果纠偏或更新控制文档时，期望执行 AI 不只是完成当前修改，还要学习其中的实践要求，并把可复用要求沉淀到项目级规则、模板和知识文档中。
- 用户强调：不一定是控制文档更新才需要学习；每一次对作品修改方向、效果控制、审美取向和生产方式的普通对话指令，都应该被当作经验来源。
- 用户不要求 AI 先判断这些经验是否“客观正确”再沉淀；项目应先按用户最新实践要求记录，并在后续创作中继续迭代。
- 用户希望项目能逐轮积累记忆，减少后续反复解释“怎么做、不要怎么做、喜欢什么效果”。
- 讨论界面、动画和运动策略时，用户默认选择纯文字、参数和具体场景解释，不主动打开浏览器可视化伴侣或网页示意；只有用户当轮明确要求动态对比、网页原型或可视化说明时才使用。
- 用户希望新经验可以覆盖旧经验：当新实践要求和旧规则冲突时，以新要求为准更新、覆盖或标注旧规则已被替换，而不是长期保留互相打架的经验。
- 用户会提供口播背后的原始大素材。用户期望画面不只复述已经提炼过的口播文案，还要从原始素材中提取更多细节，用来补充画面中的图解、流程、判断标准和执行动作。
- 用户当前以横屏视频为主，但明确要求兼容竖屏手机用户观看横版内容：画面缩小后仍要看得清，字体、节点和重点信息要足够大。
- 用户认为当前画面偏空、画面占用不满、重点不够明显；优化方向是更高信息密度、更大的关键字、更丰富的图解关系，而不是稀疏文字卡。
- 用户反复强调应使用图片化表达、路径图、关系图、流程图、箭头、结构图等可视化方式，不能只依赖文字和卡片。
- 用户要求程序动画只使用 Remotion：它可以单独制作和导出，也可以输出透明或全屏资产，再进入 Cap 上层覆盖轨。
- 用户强调动效是讲解的辅助，不是替代；项目后续应明确“讲解主线”和“动效包装”的分工。
- 新作品先按表达任务选择合适的 Remotion 组件；覆盖前必须划定主表达区域，不能和基础画面重复争夺焦点。
- 用户希望控制文档是“有限自由度执行蓝图”：我负责思考和规划，文档写清场景、文案、排版、图形关系、动效节拍和引擎分工；执行 AI 负责照蓝图做，可在边界内优化，但不能随意发挥。
- 用户不接受 Remotion 贴片式叠加：如果动画和基础画面重复、重叠、遮挡或停留太短，即使技术上接入成功，也是减分项。
- Remotion 必须承担明确区域的主表达；先处理基础画面的同类信息，再加入动画，不能覆盖一层语义重复的内容。
- 用户要的是专业化重绘和语义转译：截图里的箭头、红框和手画线代表意图，不代表最终视觉素材；任何新动画都必须避开文字遮挡和低级重叠。
- 观众可见文案要像讲解内容，不要像工程标签：避免 `BROKEN MODE` 这类英文模式名、孤立数字和抽象词；要直接说清“错误做法是什么、正确做法是什么、观众应该记住什么”。
- 做口播精剪时，如果用户只要求“根据字幕剪视频”，默认只输出剪辑后的纯视频，不要默认把字幕烧录进画面；字幕最多作为内部对齐检查文件，除非用户明确要求导出字幕或烧录字幕。
- 口播精剪不能只按“大段内容区间”粗剪；大段内部没有说话、正在思考、组织语言的空白也必须剪掉。默认应按字幕句级时间切，句间只保留极短呼吸间隔，不能让观众看到明显停顿。
- 口播精剪删除重复时，不能把非重复语义误删。重复试说只删除多余版本，但每个独立信息点至少要保留一版，例如背景、主办方、活动名称、关键论据、结论和转折都不能因为出现在试说段里就整段删掉。
- 口播精剪里没有讲话的空镜头默认按 0.1 秒极紧标准处理，尽可能不出现空镜和不说话的停顿；0.3 秒已经偏长，除非用户明确要求保留情绪停顿，否则应继续切掉。
- 口播精剪不能只删除“没有声音”的空白，也要删除“有声音但语义重复”的废弃试说。例如重复起头、重新组织语言、前面说错后后面又说了一遍的内容，都应保留更顺的一版，删除多余版本。
- 口播精剪最终交付前必须做静音复查：至少用 `silencedetect` 检查是否仍有 0.15 秒以上静默；如果正文里还有明显残留，应继续二次收紧，而不是把中间版本当最终版。
- 口播精剪的优先级是先保证内容完整，再压缩冗余。不能为了剪短，把只出现一次的独立信息、完整句尾、情绪表达、限定条件或解释性短句删掉；前后两条字幕合起来才构成完整表达时，应作为一个语义单元保留。
- 用户把“精确剪辑”定义为粗剪之后的内容导演：不仅删除停顿和重说，还要恢复 ASR 错词、判断知识与信任价值、压缩口水话、重新排列补录内容，并让整片沿一条主线自然推进。语气词和连接词按语义功能判断，不能用关键词批量删除；剪口必须保护正确口播、完整词句和音画同步。
- 用户希望后续口播剪辑可以吸收结构化粗剪管线的做法：先写剪辑简报和审稿决策表，再生成剪辑清单和导出文件。这样做的原因是先把“保留什么、删除什么、为什么删除”讲清楚，可以减少误删独立语义、误删完整句尾和音画不同步等问题。
- 用户更看重剪辑结果的内容完整和可理解，而不只是技术上剪得紧。剪得紧是手段，最终目的是让观众持续听到有效内容，同时不丢背景、转折、结论和情绪落点。
- 用户明确要求：口播里关于个人性格、做事方式、个人形象和价值取向的描述属于人格塑造与信任建立，不是口水话，精剪时应保留。可以删除的是其中附带的“嗯、呃、啊”、拖音、重复词、废弃起头和没有增加含义的绕述，不能为了提高知识密度把人物本身剪没。
- 用户希望精剪先恢复内容骨架和层级，再判断是否重排语序；原片已有主线时不强行换序，只在确有章节错位或陌生观众会断线时调整。
- 用户说“粗剪”并同时提供视频与 SRT 时，默认任务仅包括去除无讲话空镜、压缩气口、删除废弃试说和语义重复、按指定顺序拼接多个源视频；不要自行进入 Remotion、字幕烧录或画面包装。只有用户明确提出动画或画面制作时，才切换到动画工作流。
- 多个视频共用一条合并后 SRT 时，必须按用户给定顺序用各源视频精确时长计算累计偏移，把 SRT 的全局时间映射回每个源视频；分界处要单独复核，避免漏句、重句和音画错位。
- 教程口播里与连续屏幕操作对应的重复动作词不等于废弃重录。像“再删掉”“再选择一个动画”如果对应画面中的下一步操作，应保留；真正要删的是录坏后重新说了一遍的同义内容。
- 用户不希望为了单次口播精剪临时安装新的 ASR 引擎。若没有可直接调用的豆包 / 剪映 / 其他 ASR 输出，应先做波形静音粗剪，并等待用户提供 SRT 后再做语义重复删除；不要用安装本地 Whisper、faster-whisper 等方式绕过用户的工具偏好。
- 用户认可“把豆包输入法当黑盒识别器，再由外部程序补时间轴”的长期方案。落地时应优先采用后处理流程：抽音频、按人声停顿切段、记录每段时间、通过虚拟麦克风喂给豆包输入法、收集文字并合成 SRT；不建议逆向豆包私有接口，也不要在缺少虚拟音频设备时承诺自动文件转 SRT。
- 用户要的是可以从一份原始视频开始的完整自动流程：原始媒体新 ASR / SRT -> 虚拟粗剪 -> 虚拟精剪 -> 确认剪辑疑难 -> 冻结 EDL -> 一次渲染无字幕成片 -> 风险分级校验 -> 术语及错词校对 -> 固定格式字幕。即使用户提供旧 SRT，只要当轮要求验证完整流程，原始媒体仍须重新识别，旧 SRT 只做交叉校对；无字幕成片是否完整重识别则按重排、短剪口、同步和映射风险决定。
- 用户认可的当前文字识别质量基准是剪映 SRT，不接受 Apple Speech 作为主识别、置信度比较、第二识别源或交叉校对来源。火山引擎大模型录音文件识别极速版作为无 GUI 技术默认，仍必须用人工校对样本与剪映比较，不能因为同属字节就假定效果一致。
- 用户要求火山引擎 ASR 凭据只做一次本机配置，后续 SRT 识别任务直接读取，不再反复询问。凭据必须放在项目外的私密文件中，不进入 Git、作品目录、日志或回复，也不能为了排错直接打印。
- 用户已选择接入火山引擎大模型录音文件识别极速版。日常本地媒体默认抽取音频后用 Base64 直传，避免为普通文件增加 TOS 环节；标准版仅作超限文件、受控 URL 或明确优先低成本时的备选。极速版的文字质量仍需和剪映人工样本比较，不因已接入就默认准确率达标。
- 用户当前只允许使用火山引擎已有试用包，不要求也不授权自动开通后付费。试用额度不足或即将产生额外费用时，必须先说明成本和替代方案，再等待用户决策。
- 用户的固定字幕习惯是 16:9 画布、思源黑体、白字黑描边和黑色阴影，剪映参考参数为字号 5、X=0、Y=-793、描边 40、阴影不透明度 75%、模糊度 15%、距离 5、角度 -45 度。标准 16:9 源视频必须满屏保留，字幕直接叠在画面下方安全区，不得为了字幕缩小画面或强加黑框；只有非 16:9 源视频才等比缩放并利用画布余量放字幕。烧录前必须先提交专名和错词疑难清单，用户未指出的条目按当前文字接受。
- 用户不希望视频处理过程一直堆积中间文件。剪辑、转码、渲染完成后，应主动删除无复用价值的临时音频、分片、chunk、失败输出和 Git 临时垃圾；只保留当前可用成品、必要分析记录和用户明确需要的素材。
- 用户要求所有粗剪、精剪及其他媒体成片就近输出到输入视频所在目录，不放在本项目的作品输出目录。项目内无论 `输入/` 还是 `输出/` 都只保存文字型回溯记录，例如素材路径索引、ASR/SRT、JSON、EDL、剪辑决策和质检报告；原始媒体不复制进项目，最终媒体也不在项目内长期保存，以避免多个作品持续占用磁盘空间。
- 用户把字幕错词检查流程命名为“修正SRT字幕”。以后出现该触发词时，保留机器识别原稿，逐条检查专名、英文、数字、术语、同音错词、上下文、断句和剪口；确定错误直接写入修正草稿，不确定项按时码列出候选和依据让用户选择，确认后再生成正式校对 SRT。该流程只处理文字准确性，不自动烧录字幕，也不把口语改写成另一篇文案。
- 用户把确认后的字幕压制流程命名为“字幕的烧录”。以后出现该触发词时，使用正式校对 SRT，把横屏成片统一为 16:9：标准 16:9 源画面直接满屏并在画面内叠字幕，非 16:9 源画面等比完整保留并优先利用下方黑色余量。字幕使用思源黑体加粗、白字黑描边和黑色阴影。默认只输出中英双语版，中文在上、英文在下；只有用户明确要求中文版时才额外或单独生成。首次样式或样式变化先出一份双语短预览，用户指定时长时按指定值执行，未指定时约 10 秒，确认后再渲染全片。
- 用户要求把“保真校对稿”和“屏幕展示字幕”分开：校对 SRT 可以保留较长 ASR 条目和真实口语，烧录前必须使用原始 JSON 的词级时间戳跨条恢复连续词流，再按气口、完整意群和屏幕长度重新分段。中文通常约 8-18 字、1-4 秒、单行；不得拆开词组、专名、数字单位和句法搭配，也不得按字符比例平均切时间。
- 烧录展示字幕允许省略无意义的“啊、嗯、呃”、拖音、口吃和紧邻自我修正；完整语义若在音频中重复数秒，应回到精剪处理音视频，不能只隐藏字幕。中文默认不加停顿标点；英文也默认不加句末句号和非必要逗号，长句优先拆条。撇号、连字符、小数点、版本号和网址符号因承载词义而保留。
- 用户说“粗剪、精剪、修正字幕”时，表达的是同一条最终成片依次经历三个内部阶段，而不是要三个独立成品。默认只交付经历完整流程后的最终成片和正式校对 SRT；前两阶段视频及字幕草稿都是临时中间件，除非用户明确要求阶段验收或对比，否则不长期保留、不作为交付结果。
- 用户提供的直播、访谈或作品点评视频可能包含“无字幕但正在播放作品”的区间。此时有声音本身就代表正在展示效果，必须保留；粗剪只能删除同时没有有效声音和字幕内容的空白，精剪也不能为了压口水话破坏作品播放的连续性。
- 用户判断“气口 / 演示”时重视区间长度：有 ASR 文字但声音异常弱的片段通常很短，约 `1-2` 秒，可作为气口、误识别或废弃试说候选；真正的作品、音效或操作演示通常持续更长，并伴随连续声音或画面变化。时长不能单独决定删除，仍须与词级文字、波形声音类型、画面和前后语境共同判断。
- 用户确认完整剪辑采用“先虚拟剪辑、后统一渲染”：粗剪 EDL、精剪重排和剪辑疑难先在文字与时间轴层完成，冻结后只渲染一次无字幕成片；会影响音视频的疑问在渲染前确认，只影响字幕文字的疑问在烧录前确认。成片是否完整重做 ASR 按重排复杂度、短剪口数量、同步风险和 EDL 冲突决定。
- 用户希望直播和访谈成片的听感响度一致、适合持续观看。多人音量不同的素材不能只整体加减音量，应先温和拉齐动态，再统一到适合网络视频的响度；默认参考 `-16 LUFS` 和 `-1.5 dBTP`，同时保护音乐演示的自然动态。
- 用户希望组件设计以第一性目的为中心，不先按“科技博主、财经博主、知识博主”等行业标签套风格。组件风格应优先按观众效果分类，例如让观众更好理解、获得信任、觉得炫酷、照着行动、记住重点、做出选择、意识到风险或完成复盘。
- 用户接受知识讲解和炫酷动画并存：默认目标不是固定成某种“知识博主风格”，而是根据当前画面任务选择合适的观众效果。炫酷可以是正当目标，但必须服务解释和观看体验，不能为了动效牺牲清晰度。
- 用户希望后续开发新组件时，同时沉淀组件输入 schema、风格 preset、适用场景、禁用场景和 AI / skill 控制方式；长期方向是一个通用动画导演能力控制多个组件，而不是每个组件都拆一个独立 skill。
- 用户对组件调用的理想流程是两阶段：先由顶层动画导演读取指定时间段 ASR 和用户需求，判断根本目的与观众效果，推荐 1-3 个候选组件并说明作用、观众感受和风险；用户确认组件后，再读取该组件自己的 schema / preset / 示例规则，生成结构化输入并进入制作。
- 用户希望组件库具备自动进化机制：当现有组件 schema 无法满足新需求时，AI 应指出缺口，判断这是一次性适配、组件升级还是拆新组件，并说明升级后对观众效果和作品质量的提升以及复杂度风险，让用户决策后再沉淀到组件规则。
- 用户希望动画导演把信息任务与观众情绪分开判断：`communicationGoal` 决定要解释、比较、证明、选择、行动、警示、复盘还是记忆，`emotionalTone` 决定清晰、冷静、可信、 energetic、科技、紧迫或完成感；两者可以同时成立。
- ASR 没有展开但画面需要的解释可以补充，不过事实、数字和案例必须可追溯；画面内容应区分 ASR、上下文、源材料、编辑性补充和纯示意。
- 用户明确认可 AI 不应机械服从字面指令。共同目标是把作品做得更好，让观众更容易理解、获得价值，并提升完播、点赞、收藏、评论和传播；当用户表层要求可能伤害这个目标时，AI 应基于第一性原理提出质疑、说明风险和更优方案。
