# 踩坑记录

本文件记录制作过程中遇到的问题和解决方式。

## 已知问题

### 中文标题断行

问题：标题中的关键短语可能被自动换行拆开，出现类似“起 / 点”的难看断行。

处理：

- 标题写完后必须在预览中检查。
- 关键短语尽量保持在同一行。
- 必要时调整文案、容器宽度、字号或行高。

### 单一 index.html 不利于复用

问题：当前第一版工程中所有内容集中在一个 `index.html`，可以播放，但后续不利于组件复用和 Studio 中管理。

处理：

- 后续作品尽量拆分 `compositions/`。
- 常用画面抽象成模板组件。

### 缺少 FFmpeg 无法导出 MP4

问题：动画或成片渲染流程显示缺少 FFmpeg / FFprobe。

处理：

```bash
brew install ffmpeg
```

### 仍在制作的作品不要提前归档

问题：如果用户还没有确认作品结束，就把上一轮工程放进 `归档/`，会造成误解：好像这条作品已经结束，只剩复盘。

处理：

- 当前仍在制作的内容，应放在 `作品/编号_主题/制作/` 中继续迭代。
- `归档/` 只放用户确认结束、废弃或不再继续的材料。
- 沟通中产生的经验，写入 `知识沉淀/` 和 `规范/`，不要把“经验沉淀”等同于“项目归档”。

### 无 ASR 时只能做草拟时间轴

问题：没有真实音频或 ASR 时，Remotion 场景时间只能按内容结构估算，无法做到口播精确对齐。

处理：

- 草拟阶段可以用章节级时间轴。
- 正式制作前需要导入口播音频或视频。
- 生成 ASR 后再调整 `data-start` 和 `data-duration`。

### 真实 SRT 到位后不能继续沿用短草稿

问题：当前作品旧画面只有 132 秒，但真实配音 SRT 是 16 分钟左右。如果只把总时长拉长，单屏会停留太久，像静态 PPT。

处理：

- 先按 SRT 找内容段落边界。
- 把长口播拆成更多画面段落，而不是简单延长旧 12 屏。
- 当前作品从 12 屏扩为 18 屏，并把总时长设为 970 秒。
- 后续要继续观察哪些长段仍然太静，再增加局部高亮或中段刷新点。

### Remotion 资产生成成功不等于 Cap 覆盖成功

问题：Remotion 已经成功渲染透明 WebM，单独查看静帧也有内容，但在 Cap 覆盖轨中仍可能因为解码、路径、时间或层级而不可见。如果只看文件存在，就容易误判为“已经接入”。

处理：

- Remotion 输出后必须回到 Cap 预览抽查实际入点、中段和完整态。
- 覆盖记录必须保存绝对路径、T2 时间、层级、分辨率、帧率和内容哈希。
- 如果透明 WebM 在 Cap 渲染链里不可见，先检查 alpha 解码和 Motion 层，再决定改为 PNG 阶段序列。
- PNG 阶段序列也要检查位置，不能因为是 Remotion 资产就允许遮挡标题、副标题、字幕或正文。
- 不要宣称“已经用了 Remotion 动画”，除非截图里能看到它确实进入了画面。

### Git 临时包会把磁盘突然吃满

问题：长视频处理后磁盘从约 20G 可用突然变成满盘，表面看当前作品只新增了一个 1.9G 输出文件，但 `/Users/a1/Documents/老胡/.git/objects/pack/` 中出现大量 `tmp_pack_*`，`git count-objects -vH` 显示 `size-garbage` 约 19G。

原因：Git 打包 / repack / gc 过程中遇到大量或大体积对象时，可能生成临时 pack；如果过程被空间不足或其他原因中断，这些临时文件会留在 `.git/objects` 里。它们不是用户素材，也不是有效作品输出，但会直接占满磁盘。

处理：

- 磁盘异常减少时，除了查视频输出和缓存，还要立刻查 `.git/objects/pack/tmp_pack_*` 和 `git count-objects -vH`。
- 确认没有 `git / pack-objects / index-pack` 进程运行后，再清理 Git 报告为 garbage 的临时对象。
- 后续视频、渲染、粗剪产物不要进入 Git 跟踪范围；大文件只放作品目录和输出目录，必要时用 `.gitignore` 排除。
- 每次长视频任务结束后都要复查 `df -h`、当前作品大文件和 Git garbage，避免把临时占用留到下一轮。

### 大量 select / aselect 切口会积累音画取整偏差

问题：长口播存在数百个短保留区间时，如果在一个批次里分别使用 `select` 和 `aselect` 选帧，再用 `N/(fps*TB)`、`N/SR/TB` 连续重建时间戳，视频帧和 AAC 音频帧的取整误差会逐段累积。本次初稿虽然完整解码且没有长静音，但单批音视频时长差最大达到 0.137 秒，存在嘴型逐步偏移的风险。

处理：

- 每个保留区间分别使用同一组起止时间执行 `trim / atrim`。
- 每个区间分别执行 `setpts=PTS-STARTPTS` 和 `asetpts=PTS-STARTPTS`，再按音画成对顺序交给 concat。
- 批次渲染后用 `ffprobe` 比较每个批次的视频、音频起点和时长，不能只检查最终容器总时长。
- 本次改用成对裁切后，30 个批次起点均为 0，最大音视频时长差从 0.137 秒降至 0.036 秒。
- concat 出现 `Non-monotonic DTS` 后仍需完整解码、双流起点、静音和关键章节抽帧验证，不能只凭警告判断成败。

补充验证：即使已经改成逐段 `trim / atrim`，如果 30fps 视频仍按任意毫秒边界裁切、每批分别编码 AAC，再把多个 MP4 批次流复制拼接，帧取整和每批音频编码延迟仍可能继续累积。本次 828—861 个短片段的旧成片比 EDL 多出约 5.21 秒，并出现人物嘴型和声音错位。

固定修复：

- 先把每个保留区间量化到源视频帧边界；音频使用与该视频帧完全相同的边界。
- 30fps、48kHz 音频对应每帧 1600 个采样点，可用同一帧编号计算 `start_frame / end_frame` 与 `start_sample / end_sample`。
- 分批中间件使用 PCM 音频，不在每个批次分别编码 AAC；全部批次拼好后只统一编码一次 AAC。
- 最终成片时长与 EDL 预计时长的差异应不超过一个视频帧加一个音频帧；超出即视为导出失败，不能只凭“两个最终流时长接近”判断同步正常。
- 本次修复后，最终成片与 EDL 只差约 0.054 秒，音视频流起点均为 0，两条流时长差约 0.022 秒。

### 源片保留 0.1 秒气口不保证成片仍是 0.1 秒

问题：静音区间两侧各保留 `0.05` 秒时，源片计算结果是 `0.1` 秒气口；但逐区间 `trim / atrim + concat` 后，视频帧取整和 concat 对较短音频的补齐可能把个别切口拉长。本次有一处源片约 `0.21` 秒的静音，理论保留 `0.1` 秒，成片复查却达到 `0.245` 秒。

处理：

- 裁切清单通过不等于成片气口通过，最终文件必须重新执行 `silencedetect`。
- 命中超过标准的静音时，要先根据累计保留时长映射回原始区间，确认是哪个切口，不要全片盲目继续压缩。
- 只把命中的切口改为不保留气口或更小气口，再重渲染受影响批次；其他自然气口维持原规则。
- 修正后再次检查完整解码、双流起点、字幕覆盖和批次音画时长差，避免为了消灭静音引入内容截断或音画漂移。

### 单字级剪口可能留下 AAC 辅音，微调毫秒数仍会重复

问题：在“点，就 / 就是”这类相邻重复音节之间切割时，即使 EDL 起止时间对准词级时间戳，AAC 帧和重编码边界仍可能保留十几毫秒的辅音。成片听起来会变成“就就是”。连续把同一个切口前移几十毫秒，不一定能稳定解决，还可能开始损伤前一个正确词。

处理：

- 成片必须重新 ASR，并把识别结果与 EDL 映射文本交叉检查；单看源字幕和剪辑清单发现不了这种边界残留。
- 如果同一个单字边界两次微调仍残留，不再继续追逐毫秒数。改为保留前一版完整短语，删除后一段完整重复主语，或反过来保留后一版完整表达。
- 优先在“完整词组 / 完整分句”边界拼接，例如保留“就是场景资产”，再接“现在有一个理论”，不要在两个“就”字中间硬切。
- 修正后重新识别受影响成片，确认重复音节消失，再做完整解码、静音和包连续性验证。

### 最终 MP4 的视频起点可能晚一个编码重排帧

问题：分批 HEVC 编码、拼接并重新编码音频后，音频流可能从 `0.000000` 开始，而视频流从约 `0.042` 秒开始。肉眼未必明显，但不应把它当成正常结果直接交付。

处理：

- 先确认视频和音频包本身连续，没有累计漂移；不要只看容器时长。
- 若只是视频包整体起点偏移，可在最终无损封装时对视频使用 `setts=pts=PTS-STARTPTS:dts=DTS-STARTDTS`，音频保持原时间戳。
- 不要用会把所有流一起平移的方案掩盖问题，否则可能把音频再次推迟。
- 重新封装后必须复查双流起点、完整解码、包间隙和音视频时长差。

### 用场景标签整组删除会误伤独立信息点

问题：精剪把 cue 2–4 统一标成“训练营和头像引导属于弱推广”，结果不仅删掉推广语，也删掉了“Agent 安装已经讲过，遇到的相关问题都能在这里找到答案”的有效说明。另一个 cue 后半句自称“说一些口水话”，整条删除时又误伤了前半句“很多内容生产过程都有 AI 介入”的方法总结。

原因：删除判断停留在整条 SRT 或场景标签，没有继续拆到最小语义单元；把“这段出现推广 / CTA / 口水话”错误地等同于“这段所有文字都没有价值”。

固定修复：

- 精剪删除必须落到最小语义单元，混合条目先拆分再判断，禁止整组 cue 一刀切。
- 推广场景中的答案入口、适用边界和资源说明仍按信息价值判断；转化动作、互动引导属于发布策略，用户未明确要求去推广时默认保留或列为待确认。
- 每次精剪冻结前，以粗剪 EDL 为基线生成“粗剪保留、精剪删除”的全量词级差异，逐项审查；不能只通读精剪后的目标稿，因为目标稿看不到已经被删掉的内容。
- 同一句前半段有方法、观点或人格价值，后半段才是口水话时，只删除后半段，不能因为 cue 标签而整句删除。
