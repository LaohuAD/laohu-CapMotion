# Cap + Codex 口播视频工作台设计

## 1. 结论

本项目以 Cap 为桌面产品基底，不再把 Cap 放在 `参考项目/` 中作为旁路参考。现有的口播剪辑规则、ASR/SRT、EDL、Remotion、HyperFrames、字幕和知识沉淀继续保留，作为 Cap 的配套工作流与 Agent 能力。

Cap 与 Codex 保持独立：

- Cap 负责录屏、工程时间线、人工预览和调整、媒体合成与最终导出。
- Codex 负责理解口播、生成或修改 EDL、字幕和动画源码，并通过 CLI 安全修改 `.cap` 工程。
- Remotion 负责生成短动画及可复用动画模板，不负责整条长视频的最终合成。
- 人工负责选择、判断、拖拽和验收，不要求在 Cap 内重新实现聊天或语音 Agent。

核心架构是“统一工程协议，不统一运行时”。Cap 保留 Rust/WGPU/VideoToolbox 媒体管线，Remotion 保留 React/Chromium 动画生态，双方通过稳定的数据模型、版本化命令和渲染缓存协作。

## 2. 用户目标

用户希望把目前分散的流程收敛为一套可视化、可追溯、可由 Agent 操作的桌面工作台：

1. 在 Cap 中完成录屏，并能手动控制鼠标点击放大，不再只能依赖自动点击放大。
2. 录制后直接在原始 `.cap` 工程上进行字幕识别、粗剪、精剪、字幕修正和字幕烧录，避免先导出一小时原视频再二次处理。
3. Codex 可以读取和修改 `.cap` 工程，人工可以在 Cap 中查看时间线、拖动剪口、调整字幕和恢复误删内容。
4. Codex 可以针对具体片段编写 Remotion 动画，Cap 可以预览、移动、拉长、缩短和调整常用参数。
5. 用户验收过的动画可以沉淀为参数化模板；下一条视频优先复用已验收模板，没有合适模板时才创建新动画。
6. 最终仍由 Cap 统一合成长视频，保证质量、速度和音画同步。

## 3. 非目标

第一阶段不做以下事情：

- 不在 Cap 中嵌入 Codex 对话框或语音输入框。
- 不把整个 Cap 改写成 React/Remotion 浏览器编辑器。
- 不把 Remotion 重写为 Rust/WGPU 动画引擎。
- 不允许 Codex 直接覆盖整个工程配置文件。
- 不把 MOV、WebM 等渲染缓存当作动画唯一源文件。
- 不在第一版复制 Premiere、剪映或 After Effects 的全部高级动画参数。
- 不因已有模板而强制套用；模板必须先满足当前片段表达目标。

## 4. 产品边界

### 4.1 Cap

Cap 是产品主体，提供：

- macOS 优先的录屏、摄像头、麦克风和系统声音采集。
- 视频、音频、字幕、缩放和动画轨道。
- 时间线拖拽、修剪、缩放、层级和属性编辑。
- 项目保存、版本记录、外部变更重载和冲突提示。
- 低延迟预览和最终高质量导出。

### 4.2 Codex

Codex 通过本地 CLI 和工程文件工作，提供：

- 新 ASR、SRT 修正、剪辑审稿和 EDL 生成。
- 基于 EDL 修改视频保留区间和顺序。
- 读取用户在 Cap 中完成的最新修改。
- 创建或修改 Remotion 动画源码。
- 更新动画实例参数并请求局部重渲染。
- 把用户验收的动画提升为模板候选。

### 4.3 Remotion

Remotion 是动画生成器，不是 Cap 的主时间线：

- 动画源码和参数是事实来源。
- 渲染结果是可丢弃、可重建的缓存。
- 动画以透明叠加、完整图解或静态图卡形式进入 Cap。
- 复杂设计修改由 Codex 修改源码；高频参数由 Cap 属性面板调整。

## 6. 动画三层模型

每一个动画由三层组成：

### 6.1 动画定义 MotionDefinition

记录可复现的动画来源：

- 唯一标识和版本。
- 渲染器类型，例如 `remotion`。
- Remotion 入口、Composition ID 和源码位置。
- 参数 Schema、默认参数和公开参数。
- 最短、默认和最长时长。
- 时长策略及入场、展示、退场区间。
- 模板状态：临时、已验收、已发布或已弃用。

### 6.2 时间线实例 MotionSegment

记录某个动画在当前作品中的使用方式：

- 实例 ID。
- 动画定义引用及版本。
- 开始时间和结束时间。
- 图层顺序。
- 位置、缩放、旋转、透明度和裁切。
- 当前实例参数。
- 时长策略。
- 当前渲染缓存引用和状态。

### 6.3 渲染缓存 MotionArtifact

记录可删除、可重建的媒体结果：

- 动画定义版本、参数、时长、尺寸和帧率的内容哈希。
- 预览或最终用途。
- 媒体格式、绝对或工程相对路径。
- Alpha、分辨率、帧率和时长元数据。
- `ready`、`rendering`、`stale` 或 `failed` 状态。

移动动画实例不改变内容哈希，不触发 Remotion 重渲染。修改公开参数、动画定义、响应式时长、尺寸或帧率时，旧缓存标记为 `stale`，只重渲染该动画。

通用变换采用输出画布像素坐标：`x/y` 是相对画布中心的像素偏移，`scaleX/scaleY` 是相对完整画布的缩放，`rotation` 使用角度。预览和导出都由同一个原生 MotionLayer 把这些值转换为 GPU 合成参数，前端不得再叠加一套 HTML 视频预览。

## 7. MotionTrack 交互

MotionTrack 在交互上与 ZoomTrack 保持一致：

- 拖动轨道块：改变开始和结束时间，不重渲染。
- 拖动左、右边界：根据时长策略调整动画时长。
- 画布拖动：改变 X/Y。
- 控制点：改变缩放和旋转。
- 属性面板：编辑透明度、层级和公开参数。
- 轨道块显示缓存状态，过期或渲染中时不阻止继续编辑。

时长支持三种明确策略：

1. `responsive`：固定入场和退场，伸缩中间展示阶段；模板默认采用此策略。
2. `retime`：整体加速或减速；适合连续路径、循环和节奏动画。
3. `trim`：只改变可见素材范围；适合导入的普通媒体。

`responsive` 动画必须声明最短时长。用户拖短到最短时长以下时，Cap 应夹紧边界并明确提示，不能静默破坏入场或退场。

## 8. 参数编辑

Cap 始终提供以下通用参数：

- 时间、位置、缩放、旋转。
- 透明度、层级、混合和裁切。
- 时长策略和素材入点。

动画定义可通过 JSON Schema 或等价的类型化 Schema 声明公开参数：

- 文字、颜色、布尔值、枚举和数字范围。
- 图片、截图、视频和图标素材槽。
- 入场方向、动画强度和阶段时长。

Cap 根据 Schema 自动生成简洁的属性控件。未参数化的临时动画只显示通用参数；内部结构和审美调整继续由 Codex 修改源码。被用户验收后，Codex 可以把稳定、频繁修改的值提升为公开参数。

## 9. 人工与 Codex 的工程协作

工程修改采用版本化局部事务：

1. `projectRevision` 与时间线保存在同一份 `project-config.json` 中，由一次原子替换共同提交；旧工程缺少该字段时按 `0` 读取。
2. CLI 修改必须携带 `expectedRevision`。
3. 如果工程已经被用户修改，CLI 返回结构化冲突，不允许覆盖。
4. Cap 保存未落盘编辑后再应用外部事务。
5. Cap 监听外部工程版本变化并热重载无冲突的更新。
6. 所有修改记录操作者、时间、目标对象和补丁，支持审计与撤销。

CLI 优先提供领域命令，而不是暴露整份 JSON 覆盖：

```text
cap project inspect <project>
cap project validate <project>
cap project transaction apply <project> --expected-revision <n> --patch <file>
cap motion definition register <project> --expected-revision <n> ...
cap motion add <project> --expected-revision <n> --definition-id <id> --start <seconds> --duration <seconds>
cap motion move <project> --expected-revision <n> --segment <id> --start <seconds>
cap motion resize <project> --expected-revision <n> --segment <id> --duration <seconds>
cap motion props set <project> --expected-revision <n> --segment <id> --props-json <json>
cap motion render <project> --expected-revision <n> --segment <id> --quality preview|final
```

工程规则放在 `cap-project`，可独立测试的命令协议放在 `cap-motion-cli`，现有 `cap` 二进制只负责挂载子命令和输出。`motion render` 已实现选中实例的局部渲染、内容哈希缓存、preview/final 产物和 revision-safe 工程回写；命中缓存时不重复启动 Remotion。缓存键同时包含 `src/`、`public/`、Remotion 配置和依赖锁文件的实际内容指纹，源码变更不会错误复用旧缓存。

## 10. Remotion 预览与渲染

第一阶段不把 `@remotion/player` 嵌入 Cap 主预览。Cap 预览与最终导出使用同一套媒体合成路径，避免浏览器预览与最终成片不一致。

已落地的媒体桥使用 Cap 原生 `RendererLayers` 中的 MotionLayer：它按工程时间选择活动实例、把时间映射到缓存本地时间、解码动画帧，并在摄像头/屏幕内容之后、字幕和编辑标注之前做 Alpha 合成。透明素材强制走软件 FFmpeg RGBA 解码，避免 VideoToolbox 或 Media Foundation 的 NV12 路径丢失 Alpha；无透明素材仍可使用平台硬件解码。

渲染分为：

- 预览缓存：低分辨率或较低成本的透明媒体，优先快速返回。
- 最终缓存：全分辨率高质量透明媒体。
- 无透明背景动画或 B-roll：使用适合硬件解码的 H.264/HEVC。
- macOS 透明中间件：首选 ProRes 4444 MOV；实际预览格式在实现阶段通过随机定位、解码延迟、体积和渲染时间基准确定。

当前已验收的编码是：预览使用 960×540 VP8 WebM（`alpha_mode=1`），最终缓存使用 1920×1080 ProRes 4444 MOV。二者都由同一个 Composition 和 props 生成，只改变质量档位。

最终导出只发生一次有损成片编码：Remotion 动画使用高质量或近无损中间件，Cap 解码并与屏幕、摄像头、字幕和音频统一合成，最终通过 Cap 的原生导出管线编码。

## 11. 录制时手动放大

保留现有自动点击放大设置，同时新增录制期手动放大模式：

- 全局快捷键切换放大状态。
- 开启时以鼠标位置为中心创建或更新放大段。
- 录制界面显示最终可见区域框；框外区域变暗，但暗化提示不进入录制结果。
- 再次按快捷键恢复正常区域并结束当前放大段。
- 生成的数据继续使用 Cap 的缩放轨道，录制后可以人工移动或调整时长。
- 自动放大和手动放大可以分别启用，冲突时手动操作优先。

## 12. 口播剪辑与字幕流水线

现有项目规则继续作为 Agent 层的事实来源：

```text
新 ASR
→ 粗剪 EDL
→ 内容精剪与重排
→ 剪辑疑难确认
→ 冻结 EDL
→ 写入 Cap 时间线
→ 无字幕成片复核
→ 修正 SRT
→ 字幕展示稿拆分
→ 默认双语烧录
```

第一版通过 CLI 把已确认 EDL、SRT 和动画实例写入 `.cap` 工程。Cap 负责人工调整和最终导出；Agent 不在未经确认时直接删除高风险片段。

## 13. 动画生成与模板演化

模板的形成顺序是“先做好具体片段，再抽象模板”：

1. Codex 根据口播、SRT、前后文和素材为当前片段生成具体动画。
2. Cap 载入预览缓存，用户拖动时间、位置或给 Codex自然语言反馈。
3. Codex 修改源码并局部重渲染。
4. 用户明确验收后，当前动画成为已验收案例。
5. Codex 提取稳定结构和公开参数，生成模板候选。
6. 下一条视频优先检索已验收模板，进行最小参数调整。
7. 现有模板无法满足表达目标时才创建新动画。

验收记录至少保存适用场景、表达目标、所需输入、视觉风格、参数范围、失败边界和对应成片截图。

## 14. 性能原则

- 不使用 Remotion 渲染整条长视频。
- 只对变化的短动画做增量渲染。
- 时间线移动和通用变换即时生效，不触发源码渲染。
- Cap 继续使用原生解码、WGPU 合成和平台硬件编码。
- 渲染缓存按内容哈希复用，并设置磁盘预算和自动回收。
- 导出增加 decode、render、composite、encode、mux 分阶段统计，检测硬件回退。
- 在决定替换导出架构前，必须用用户真实长视频工程进行基准测试。

## 15. 错误处理

- 工程版本冲突：拒绝写入并返回当前版本和冲突对象。
- 动画定义缺失：保留实例，显示离线占位，不删除配置。
- 缓存缺失或过期：显示占位或旧预览，后台重新生成。
- 渲染失败：保留最后可用缓存，显示错误摘要和日志路径。
- 参数不符合 Schema：拒绝事务，返回字段级错误。
- 媒体格式不支持：导入前探测并给出可执行的转码建议。
- 工程迁移失败：保留原文件并使用临时文件原子替换。
- Codex 命令超时：不得留下半应用事务。

## 16. 测试策略

### 数据层

- MotionDefinition、MotionSegment、MotionArtifact 序列化往返。
- 老工程缺少动画字段时使用默认值。
- 时长策略、最短时长和参数 Schema 校验。
- 内容哈希只在实际渲染输入变化时变化。

### 协作层

- 正确 revision 的事务成功。
- 过期 revision 被拒绝。
- 多条操作要么全部成功，要么全部失败。
- Cap 和 CLI 交替编辑不丢数据。

### 时间线与 UI

- 移动、缩放、撤销和重做。
- `responsive`、`retime`、`trim` 三种行为。
- 过期、渲染中、失败和完成状态。
- 画布变换和属性面板保持一致。

### 媒体与渲染

- Alpha 解码和合成正确。
- 预览与最终导出关键帧一致。
- 30/60fps、1080p/4K 和不同源帧率。
- 动画层与字幕、摄像头、屏幕层级正确。
- 长工程随机定位和内存占用。

### 端到端验收

- 录制一个短工程并手动创建放大段。
- Codex/CLI 导入 EDL 和字幕。
- 添加一个 Remotion 动画。
- 人工移动、拉长并修改公开参数。
- 外部命令修改后 Cap 热重载。
- 导出的视频时间、音画、Alpha、字幕和动画均正确。

## 17. 分阶段落地

### 阶段一：产品基底和安全工程接口

- 把 Cap 源码迁移到根仓库。
- 保留现有工作流资产并更新仓库文档和许可证。
- 添加 upstream。
- 建立工程 revision、事务和兼容迁移。
- 扩展 CLI 的安全检查和局部修改基础。

当前已完成：Cap 根基底、Motion 工程模型、单文件 revision、写锁、冲突拒绝、Motion 命令协议、MotionTrack、属性面板、revision 冲突提示、Remotion 局部渲染与缓存回写。完整 `cap` 二进制在当前机器上仍需安装完整 Xcode，并把本机 FFmpeg 8 切换为项目兼容的 FFmpeg 7 后做原生媒体依赖验收。

## 18. 完成标准

项目落地完成必须同时满足：

1. 根仓库可以按 Cap 上游说明构建，原有工作流资产仍可访问。
2. 用户可以在 Cap 时间线上人工调整 Agent 添加的动画。
3. 简单时间、位置和大小修改不依赖 Codex，也不触发 Remotion 重渲染。
4. 参数和响应式时长修改只重渲染受影响动画。
5. Cap 与 Codex 交替修改工程不会静默覆盖。
6. Remotion 源码、实例和渲染缓存可以相互追溯。
7. 最终导出由 Cap 完成，视频、音频、字幕和动画同步。
8. 用户验收动画可以沉淀并在后续作品中优先复用。
9. 真实工程有质量、速度、内存和缓存占用记录。
