# Cap 工程 Remotion 经典案例演示设计

## 目标

在现有约 27 秒的 Cap 工程中加入一条可直接预览、可继续人工调整的 Remotion 演示带。演示只用于观察动画能力，不要求匹配原录屏语义。

源工程：

`/Users/a1/Library/Application Support/so.cap.desktop.dev/recordings/Mi Monitor (Area) 2026-08-30 06.23 PM.cap`

## 选择方案

采用“四段经典案例串联”方案。它比单个复杂动画更适合本次测试：一次打开工程即可比较四类最常用的信息表达，同时每段仍有约 6 秒，不会快到看不清。

时间安排：

| 成片时间 | Remotion 案例 | 演示重点 |
| --- | --- | --- |
| 00:00.50–00:06.50 | `KineticStatement` | 关键词逐层进入、重点放大、结论收束 |
| 00:07.00–00:13.00 | `CompareTransform` | 左右对比、差异强调、错误到正确的变化 |
| 00:13.50–00:19.50 | `FlowNodeGraph` | 节点生成、连线推进、流程关系建立 |
| 00:20.00–00:26.00 | `EvidenceBoard` | 截图/证据卡进入、标注聚焦、结论归纳 |

段落之间保留约 0.5 秒基础画面，用于观察动画进入和退出是否自然。

## 演示内容

全部使用通用中文示例，不读取或推断录屏内容：

- 重点标题：`先讲结论 / 再给证据 / 最后给行动`
- 左右对比：`信息堆叠` 对比 `关系清楚`
- 流程图：`问题 → 判断 → 方案 → 结果`
- 证据板：`现象 / 证据 / 结论`

每段左上角保留一个弱化的小标签，显示组件名，便于用户在 Cap 里判断自己正在看哪一种案例；标签不能抢主标题。

## Cap 写入方式

1. 保留两个原始录制 segment、摄像头、麦克风、系统声音、缩放信息和全部源媒体。
2. 只在上层 Motion/动画轨写入四个 Remotion definition 与四个 timeline segment。
3. definition 指向项目统一 Remotion workspace，不复制 `node_modules`，不创建作品级重复工程。
4. 所有写入使用 Cap CLI 的 revision-safe 命令；每次修改前读取最新 revision，避免覆盖人工改动。
5. 动画配置保存在 Cap 工程及其邻近资产目录中，不把视频二进制复制进 Git 仓库。

## 预览与验证

验证分为四层：

- 结构：四个 definition 和四个 segment 均存在，时间不越过约 27.08 秒的工程长度。
- 路由：所有动画均由 Remotion workspace 提供，不出现其他动画引擎入口。
- 行为：四段按时间依次出现，底层录屏与音频保持原顺序和原时长。
- 观感：文字无难看断行，主次清楚，进入、变化和收束完整；四段之间有可感知的类型差异。

如果 Cap 当前构建无法直接预览某个 definition，回退方案是把对应 Remotion composition 渲染成独立外部资产，再通过 Cap 的 Motion artifact 接口回填；仍不改动底层录制轨。

## 保护与回退

- 写入前复制 `project-config.json` 和 `recording-meta.json` 到工程内部的任务级备份位置，避免复制整套大媒体。
- 不删除、不移动原始媒体。
- 任一写入或预览验证失败时，恢复这两个小型配置文件，并保留失败记录，不留下半写入 Motion segment。
- 本次只修改用户指定的 Cap 工程和必要的演示配置，不改其他录制工程。

## 验收标准

用户打开该 Cap 工程后，可以在同一条约 27 秒时间线上依次看到四种经典 Remotion 动画，并能在动画轨上移动或调整段落；关闭或移除动画轨后，原始录屏和声音仍完整可用。
