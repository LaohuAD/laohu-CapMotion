# Cap 录制控制条、手动放大与摄像头可靠性设计

## 1. 结论

本次改造解决三个相互独立、但都发生在录制阶段的问题：

1. 录制控制条在录制结束后残留，以及录制仍正常进行时界面计时突然归零。
2. 手动放大时缺少持续、准确且不妨碍操作的取景提示。
3. 摄像头可能因重复初始化、被其他程序占用或权限状态不同而无法启动，但当前界面没有把原因区分清楚。

最终体验是：

- 没有活动录制时，录制控制条必须隐藏，不允许留下可拖动的倒计时残影。
- 录制计时由后端活动录制会话决定，前端热更新或窗口重新挂载不能让计时归零。
- 正常录制时，控制条默认折叠成右侧一个带红色录制圆点的小方块；鼠标悬停时向左展开，移开后重新折叠。倒计时和错误状态强制展开。
- 手动放大开启后，蓝色取景框始终显示；框内保持正常亮度，框外仍可见但压暗约 30%。覆盖层完全穿透鼠标、不抢焦点。
- 手动放大采用“柔性跟随”：鼠标在取景框中央安全区移动时画面保持稳定，接近边缘时才平滑推动取景框，停止移动后自然停稳。
- 摄像头错误区分为权限未授予、设备被其他程序占用、Cap 内部重复占用和设备初始化失败，并避免 Cap 对同一设备重复启动采集。

## 2. 已确认的问题与根因

### 2.1 控制条残留

`in-progress-recording` Webview 会在多次录制之间复用。当前前端初始化可能继续读取持久化的倒计时状态，但只在部分初始化状态下检查后端是否真的存在活动录制。因此，当录制已经结束、Webview 因热更新或重新挂载再次出现时，仍可能显示上一次的倒计时数字，并且窗口还可以拖动。

根本问题不是“隐藏动画没有结束”，而是前端显示状态没有以活动录制会话为事实来源。

### 2.2 计时归零但成片完整

当前计时主要由前端组件的本地时间计算。录制过程中如果 Webview 重载或组件重新挂载，前端会把当前时刻重新当作开始时间，所以显示从零重新计数；后端录制器并没有停止或重建，因此最终导出的素材仍然完整。

根本问题是显示计时器和真正录制会话分离，且前端没有可恢复的会话标识和累计时长。

### 2.3 手动放大覆盖层妨碍操作

当前取景覆盖层会创建覆盖整个录制目标的透明 Webview，并用大范围阴影压暗框外区域。覆盖层本应忽略鼠标事件并且不获得焦点，但窗口创建、显示和内容状态没有形成一套可验证的生命周期；同时，取景框只反映按下快捷键时的固定位置，不能表达用户继续操作时实际希望看到的区域。

根本问题分成两层：

- 窗口层必须是持续显示但完全不参与交互的视觉提示层。
- 取景逻辑必须和最终缩放中心使用同一套可重放算法，不能只显示一个与结果无关的静态框。

### 2.4 摄像头无法启动

目前错误信息只能说明底层 `StartCapturing` 失败，不能仅凭截图断定是权限、外部程序占用还是 Cap 自己重复持有设备。界面中的“授权”也可能把设备不可用误呈现为权限问题。

因此摄像头修复必须先区分状态，再处理：

- 系统权限未授予：引导用户授权。
- 设备被其他程序占用：不反复重试抢占，明确提示关闭占用程序。
- Cap 内已有预览或录制流持有同一设备：复用现有会话或先完成内部切换，禁止重复 `StartCapturing`。
- 设备存在但初始化失败：有限次数重试后显示设备名和可操作的错误说明。

## 3. 录制会话与计时模型

### 3.1 后端是唯一事实来源

后端为每次真正开始的录制创建唯一 `sessionId`，并维护：

- `startedAt` 或等价单调时钟基线。
- 已累计暂停时长。
- 当前是否暂停。
- 当前有效 `elapsedMs`。
- 当前录制模式和生命周期状态。

前端查询当前录制时，后端返回活动会话快照。前端只负责按快照平滑刷新显示，不自行创建新的录制起点。

### 3.2 恢复与重复事件

- Webview 首次加载、热更新或重新挂载时，先查询后端。
- 后端没有活动录制时，无论前端缓存的是初始化、倒计时、录制中还是暂停，都立即隐藏控制窗口并清空临时显示状态。
- 后端存在活动录制时，用 `sessionId + elapsedMs + paused` 恢复显示。
- 同一 `sessionId` 的重复 Started 事件只能刷新状态，不能重置计时。
- 只有新的 `sessionId` 才能开始新的显示计时。
- 暂停期间计时冻结；恢复后从后端累计时长继续。

### 3.3 倒计时边界

倒计时是“准备开始”的临时状态，不等于活动录制。倒计时结束后只有后端确认创建了会话，界面才能进入录制中；如果启动失败，则进入明确错误状态并停止倒计时。

## 4. 录制控制条交互

### 4.1 折叠状态

录制开始后，控制条默认显示为靠屏幕右侧的紧凑方块：

- 主视觉为红色录制圆点。
- 整个方块都是拖动区域，用户可以改变它在屏幕边缘的位置。
- 不显示计时、麦克风、暂停、重录、删除、设置等完整控件。
- 方块只在活动录制存在时显示。

### 4.2 展开状态

- 鼠标进入方块后，控制条以右侧位置为锚点向左展开。
- 展开后保留现有录制操作和计时信息。
- 鼠标离开整个展开区域后，经过短暂防抖再折叠，避免移动到边缘按钮时闪烁。
- 用户正在按下或拖动控件时不能自动折叠。
- 倒计时、启动失败、权限提示和其他需要用户处理的错误强制展开。
- 暂停状态仍可折叠，但折叠态需要以清楚的视觉状态区别于正在录制。

### 4.3 窗口行为

- 控制条可以拖动，但非活动录制时窗口必须隐藏。
- 显示和折叠不能激活或抢走用户正在操作的软件焦点。
- 折叠时只保留小方块的可交互区域，避免透明的大窗口阻挡下面的软件。
- 展开动画只改变控制条自身，不改变录制目标、取景框或录制结果。

## 5. 手动放大取景框

### 5.1 视觉与生命周期

第一次按手动放大快捷键时：

- 以当前鼠标位置为初始中心创建手动放大段。
- 显示与最终放大范围一致的蓝色取景框。
- 框内保持原画面正常亮度。
- 框外保留完整原画面，使用约 30% 黑色遮罩压暗，帮助用户同时看见当前录制区域和外围环境。
- 取景框在整个手动放大段内持续显示，不自动消失。

第二次按同一快捷键时：

- 结束当前手动放大段。
- 隐藏取景框和压暗遮罩。
- 恢复正常全画面录制预览。

取景提示只用于操作者查看，不写进最终录制视频。

### 5.2 穿透与焦点

覆盖层可以在技术上覆盖整个目标窗口或显示器，但必须满足：

- 所有鼠标点击、滚轮、拖拽和悬停继续传给下面的真实软件。
- 覆盖层不能成为键盘焦点窗口。
- 显示、移动和隐藏覆盖层不能把当前应用切换到 Cap。
- 覆盖层不提供按钮、菜单或拖动手柄。

这意味着用户看到取景框和暗区，但操作体验仍然像覆盖层不存在一样。

## 6. 柔性跟随算法

### 6.1 用户感受

手动放大不是完全固定，也不是始终黏着鼠标：

- 鼠标在取景框中央的安全区内移动时，取景框和最终放大画面不动。
- 鼠标进入靠近边缘的缓冲区后，取景框才朝鼠标方向平滑移动。
- 鼠标越接近或越过取景框边缘，推动速度越大，但不瞬间跳动。
- 鼠标停止后，取景框缓动到目标位置并稳定。
- 取景框永远夹在源画面边界内，不露出无效区域。

用户因此可以在一个局部界面内自由点选，不产生不必要的镜头晃动；需要切换到旁边内容时，只要把鼠标推到边缘，画面就自然跟过去。

### 6.2 默认参数

第一版使用固定但集中管理的默认值：

- 放大倍数继续使用现有手动放大设置。
- 中央安全区约占取景框宽高的 60%。
- 四周各约 20% 为柔性缓冲区。
- 框外遮罩不透明度约 30%。
- 跟随采用平滑阻尼，不使用固定延迟或突然跳转。

这些值必须作为明确配置存在，方便后续根据真实录制手感调整，不能散落写死在多个前端和渲染文件里。

### 6.3 录制、预览和导出一致

柔性跟随使用确定性算法：输入是鼠标时间序列、手动放大段起止时间、初始中心、放大倍数和跟随参数，输出是随时间变化的缩放中心。

同一算法必须服务：

- 录制时取景框的实时位置。
- Cap 编辑器中的手动放大预览。
- 最终导出时的缩放中心。

录制期 Rust 端按稳定频率读取鼠标位置并更新实时取景框；项目保存足以重放该效果的数据，渲染端用录制到的鼠标事件重新计算同一路径。不能让实时框移动了，但最终成片仍使用第一次按键时的固定坐标。

### 6.4 与自动放大的关系

- 自动放大继续由点击事件和鼠标轨迹生成自动缩放段。
- 手动放大由快捷键明确开始和结束，并在该时间范围内优先于自动放大。
- 手动段结束后，自动放大恢复现有规则。
- 编辑器中用户仍可移动、拉长或缩短手动放大段。

## 7. 摄像头可靠性

### 7.1 单一设备所有权

Cap 内部建立清楚的摄像头占用状态：选择器预览、悬浮摄像头预览和正式录制不能各自无条件打开同一个设备。对于同一设备：

- 能复用同一采集会话时复用。
- 必须切换管线时先有序停止旧会话，再启动新会话。
- 并发到来的重复启动请求合并为一个操作。
- 旧请求完成后不能覆盖用户已经选择的新设备状态。

### 7.2 错误分类与界面

摄像头状态至少区分：

- 未授权。
- 设备正在被其他应用使用。
- Cap 内部正在切换或初始化。
- 设备断开。
- 初始化失败。

“授权”按钮只在系统权限确实未授予时出现。设备被占用时显示设备名称和关闭其他占用应用的提示；内部切换时显示短暂加载状态；有限重试后仍失败则允许用户重试或选择其他摄像头。

## 8. 数据兼容与迁移

- 旧工程中的 `ZoomMode::Manual { x, y }` 保持可读取，并继续表现为固定中心，避免改变已有项目的画面。
- 新录制创建支持柔性跟随的新手动模式，并带有版本化参数。
- 序列化格式必须有兼容测试；旧 Cap 工程打开、保存和再次导出不能丢失缩放段。
- 新增用户可见文字进入统一中英文翻译表；设备标识、型号、错误代码和技术字段保持原文。

## 9. 测试与验收

### 9.1 自动测试

先写失败测试，再实现：

- 无后端活动会话时，任意残留前端状态都会归一为隐藏。
- 同一 `sessionId` 重复事件或组件重新挂载不重置计时。
- 新 `sessionId` 正确开始新计时，暂停与恢复累计正确。
- 控制条折叠、悬停展开、离开折叠、倒计时和错误强制展开。
- 折叠状态的交互区域不会保留透明阻挡区。
- 柔性跟随在安全区内输出稳定中心；进入缓冲区后平滑移动；边缘正确夹紧；同一输入产生同一输出。
- 旧固定手动放大工程兼容，新柔性模式可序列化往返。
- 摄像头同设备的重复启动请求不会创建第二个采集会话，设备切换顺序正确。
- 摄像头权限、外部占用和初始化失败不会映射成同一个界面状态。

### 9.2 后台验证

开发过程中只运行无界面的 Rust 测试、前端单元测试、TypeScript 检查和生产构建，不反复启动 Cap 或抢占用户当前窗口。

### 9.3 人工验收

自动测试通过后，由用户明确同意再只启动一次可见应用，逐项检查：

1. 未录制时没有残留控制条。
2. 录制中热更新或窗口恢复后计时不归零。
3. 折叠方块可拖动，悬停展开和移开折叠自然。
4. 手动放大框持续显示，框外约 30% 暗化，底层软件仍可正常点击和输入。
5. 安全区内画面稳定，鼠标推到边缘时取景框柔和跟随，最终预览路径一致。
6. 第二次快捷键结束手动放大并隐藏覆盖层。
7. 摄像头可正常预览和录制；若被其他程序占用，错误说明准确且不会误显示为权限问题。

## 10. 实施边界

本轮只处理录制控制条、录制显示计时、手动放大取景框与路径、摄像头可靠性及相关中英文界面。不会借此改写整个录制架构、引入新的 Agent 对话窗口、改变现有自动放大风格或把取景遮罩烧进成片。
