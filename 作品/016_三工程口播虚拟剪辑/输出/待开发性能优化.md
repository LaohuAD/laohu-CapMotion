# CapMotion 性能与制作流程优化待办

状态：CapMotion 0.1.4 已完成本轮优化、Mac/Windows 打包与 GitHub 发布，本机 Mac 已更新。后续待验证项和配音方案仍保留在本文件中，不视为已经完成。

## 已测事实
大工程源素材约94分钟，剪后28分11秒。主程序physical footprint约3.9GiB、历史峰值4.2GiB；导出结束后约48秒四次采样稳定。36条源音轨按48kHz float32展开的有效样本约3.02GiB：麦克风1.01GiB、系统音2.01GiB；未含Vec容量、视频解码及界面。源码对全部源音轨解码并长期持有，导出子进程另外建立一套。机器16GiB内存，曾观测系统交换空间使用约18GiB；交换空间属于整机，不能全部归因于Cap。

单源短工程79.52秒，1080p30导出约25.17秒；主程序约586MiB，导出进程约571～598MiB，两进程采样最高约1.16GiB，结束后主程序稳定且导出进程退出。采样晚于开始约10秒，不保证捕获全部瞬时峰值，不含WebKit辅助进程。主程序历史峰值4.2GiB不是这次短导出的峰值。

结论：证据支持完整源音频常驻与重复加载是大工程主要内存负担，不能据此断言无限内存泄漏。短工程正常不能排除长工程问题。原始测量见同目录性能测量.json。

## 开发顺序
1. 先补齐监测：记录physical footprint、压缩内存及应用/导出进程组峰值，不能只看RSS和虚拟地址空间。
2. 音频按需分块解码：播放缓存当前位置附近，导出按时间轴逐块解码；完成、取消及错误均释放；避免保留整份源音频。
3. 设置缓存总量及并发上限。波形使用磁盘缓存或流式统计，不能为了画波形把整条音频常驻。缓存与临时文件只放外接工作盘。
4. 实测拖动延迟：用户操作到画面呈现的p50/p95、UI帧时间、跨片段与随机定位。已有29～30fps预览传输日志不能代表拖动延迟正常。
5. 检查字幕轨可见区域绘制（现有998条字幕全部创建）、视频解码按需加载与缓存淘汰。根据测量再决定代理媒体；代理仅供编辑，最终导出使用原素材。

## 验收
同一大工程和小工程对比：首次打开、连续播放、快速拖动、跨剪口、完整导出、取消导出及重复导出2～3次。关注峰值是否有界、完成后是否回落、内存是否逐次累积，以及音画同步、字幕与最终输出质量。共享实现需验证macOS和Windows；编译通过不代表Windows实机通过。

不把先压平成MP4再导回作为根治方案，需保留可返工的源素材与EDL。没有用户新的打包授权，不更新安装版。


## 2026-09-11 长片导出补充现场

用户截图显示 CapMotion 应用内存 40.98GB，系统提示内存不足。导出于09:44:07正常完成，输出1913229068字节。本次采样只覆盖09:41:59至09:44:44：主程序 physical footprint 约3.7GiB，导出器约3.3→3.5GiB；导出器随后退出，主程序仍约3.7GiB。系统交换空间已使用量从23508.56MiB增至结束前26029.06MiB，结束后降至11505.88MiB。交换空间为全系统指标，不能全部归因于CapMotion。

此前整段源音频加载约3GiB只能解释部分固定占用，不能解释截图40.98GB。当前采样缺少完整关联进程、驱动/图形资源和应用内存口径，尚不能确认额外增长的分配来源，也不能仅据此定性永久内存泄漏。后续优先补齐进程组和内存类别采样，再定位随导出增长的缓存或资源；不要把仅主进程RSS或少数进程footprint当成应用总内存。完整采样保存在性能测量.json。


## 2026-09-11 配音、出镜与表达训练方案（待用户决策）

用户提出：以整理通顺的字幕生成本人克隆音色配音，再分段加速原教学录屏适配新音频；音色克隆供应商与调用流程由用户后续确定。另一候选是本人根据整理稿重新录制声音和出镜，但用户不喜欢逐字照念，希望同时改善自己的表达能力。此次只记录与决策，不启动配音、重录、媒体重建或开发打包。

目标与取舍：同时追求教学清楚、制作省力、人物辨识度和长期表达进步。时长缩短不直接等于观众理解更好或传播更好，须保留关键操作和观察结果的时间；平稳的合成声音也不自动优于有重点、有情绪的本人表达。

建议先试“本人按提纲分段重讲为主，克隆音色作为局部补录备选”：从自由口述提取保真、适合口说的段落稿，再压成几个提示词；看懂后移开全文，用自己的话讲一个完整意思，允许不同措辞，最后依据实际新录音生成展示字幕。开场、关键判断与结尾优先本人声画；软件演示按操作节点与最终音频对齐。无需始终出镜；克隆配音覆盖时不要保留正在说旧台词的正脸镜头。

时间映射要求：以用户确认的新录音或新配音为新时间轴权威，逐意群绑定原录屏的点击、输入、结果出现等事件。只对适合加速的等待和重复操作局部变速，不整片按总时长等比压缩；关键点击、参数和结果必须看得清。新配音比必要操作更短时，调整讲述节奏、补充必要解释或延长观察时间，不能强行挤压演示；有声案例、音乐展示不可机械加速。重做字幕及源到成片映射，保留源素材和原工程的可追溯性。

表达训练建议：整理稿用于发现原表达中的绕路与重复，而不只是朗读成品。练习“看懂→只看关键词复述→回听找一个问题→再讲”，逐渐减少全文依赖。朗读可能改善熟练度，但不能据此保证即兴组织能力迁移。检索练习研究可为主动回忆提供间接依据，并非直接证明中文口播训练效果：https://www.nature.com/articles/s44159-022-00089-1 。

试验方式：下一条作品先取一个约1～2分钟教学单元，对比提纲重讲与克隆配音配录屏；记录制作总耗时、返工次数、本人自然感、观看者能否复述并完成关键步骤。表达进步另外看新主题首次讲述的重复、思考停顿和结构清晰度，不只看熟稿读得是否顺。方案尚未采纳，不写为永久制作规则。


## 2026-09-13 0.1.4 实施与复现记录

本轮采用项目进化与系统排错方法：原先“整份源音频约3GiB”只能解释固定负担，不能解释40.98GB现场。因此先分离连续解码、跨剪口跳读、GPU转换、编码与闲置回收，寻找最早累积点；没有把最初的 autorelease 假设直接当作修复结论。

确认的两类负担：

1. 长音轨浮点样本全量常驻。改为超过8MiB后流式写入源文件同盘的匿名临时文件，并只读映射供现有混音代码读取；音频准备并发上限2。关闭、出错或进程退出时由操作系统回收文件。仍会准备源音频，本轮没有实现“只解码当前播放区间”；后者保留为启动耗时的后续优化候选。
2. macOS 跨剪口跳读为每份源视频创建多个 AVAssetReader，访问过的源段一直保留解码器池。18个录制段的屏幕与摄像头资源因此叠加。闲置2秒后清理缓存并释放整池，关闭时取消底层读取；保留变帧率长静帧的时间信息，恢复时复用关键帧索引。Windows/MF和FFmpeg同时清理闲置帧缓存。

证据：旧0.1.3同工程导出约478.8秒时，IOSurface映射约28.4GiB、8339个区域；单源连续4000帧约292MiB稳定，单源跳读约1.3GiB。新回收测试闲置后降到2384KiB，并能恢复取帧。IOSurface映射、进程physical footprint和系统应用总内存是不同口径，不能混称“应用仅占多少”。开发构建整片导出成功：28分11.043秒音频、50732帧1080p30视频，退出码0，墙钟约999秒（同时进行软件构建，不作为独立速度基准）。89次采样的进程physical footprint最高约1.1GiB、IOSurface映射最高约3.0GiB，最后一次约1.8GiB；未出现旧版逐源累积到28.4GiB的模式。14:25起15秒抽样有正常音频能量，整片视频和音频解码检查退出码0且无错误。发布构建另做完整导出确认。

其他已实现项：字幕时间轴仅创建可见条目并保留拖动对象及相邻约束；中英轨独立字号与预设保存；手动位置控件、波形同步偏移和提词稿滚动修复；编辑器与导出器的进程内存分别采样；sidecar新鲜度检查补齐音频和解码依赖，避免安装包夹带旧导出器。

保护项：PCM逐样本等价、源音画偏移、冻结EDL、字幕正文、中英轨独立设置、变帧率长静帧与Mac持久签名。现有893个剪口的时长不因本次缓存调整而改变。新建工作工程已走通源字幕导入、原时间轴EDL写入、998条双语物化、字号和手动位置、画幅、预设保存/重用、重新读取和1080p实际预览；原工程不用于破坏性回归。

未采用或未完成：音色克隆/配音重建、整片压平替代工程、无证据的全局淡入淡出、代理媒体、拖轴延迟p50/p95专项测量、Windows真实摄像头/麦克风/GPU设备验收。本轮确定性回归通过的实现为KEEP；尚未实机覆盖的交互与Windows设备体验保持OBSERVE，不冒充完成。

构建与原始测量统一位于本项目外接盘 target/capmotion-release/，不提交媒体、安装包、个人素材或完整私有诊断日志到Git。Mac发布目标Apple Silicon，Windows发布目标x64。
