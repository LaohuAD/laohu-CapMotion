# 018 覆盖动画的执行记录

记录这轮「口播段加覆盖动画」从头到尾怎么做的。目的是以后要固化到 Skill 时，能直接从这里取步骤、判据和踩过的坑。

## 一、前置：先量出「画面什么时候在动」

动画压在画面运动上会抢焦点，所以第一件事不是设计图形，是**把画面运动标出来**。

源工程有 `timeline.zoomSegments`（本片 31 段推近/拉远）。把它按冻结的源到成片映射搬到成片时间：

```text
成片里画面在动的窗口：19 段，合计 343.5 秒
画面静止的窗口：15 段，合计 1095.7 秒，占全片 75%
```

**判断**：动画只能落在静止窗口里。这条一算出来，原先放在推近段的三段动画立刻全部作废。

## 二、再量「鼠标在哪」

底画铺满整个画布（display 3046×1672 贴宽，没有留边），右下角是摄像头，最下面是字幕。所以覆盖不可能不遮画面，只能挑**不遮鼠标、也不遮正在讲的地方**。

各录制段目录里有 `cursor.json`，字段 `moves[] = {time_ms, x, y}`（归一化坐标，段本地时钟）。按冻结 EDL 映射到成片时间后：

```text
前半段  0–540 秒      鼠标停在右上角     x ≈ 0.90   y ≈ 0.14–0.24
后半段  540–1454 秒   鼠标在中间偏左     x ≈ 0.24–0.65   y ≈ 0.28–0.89
```

**判断**：前半段用全幅压暗 + 居中图形（鼠标停在角落，不碍事）；后半段改用**右侧竖条面板 x ≈ 0.68–0.96、y ≈ 0.06–0.62**，避开鼠标、摄像头和字幕。

## 三、把口播结构转成图形形态

扫描静止窗口里的口播，找出五类可视觉化的结构，归成八种可传参形态：

| 口播结构 | 信号 | 形态 |
| --- | --- | --- |
| 枚举 | 第一…第二…还有 | `list` 逐条点亮 |
| 观点判断 | 根本的还是…、最重要的是… | `statement` 大字卡 |
| 对比对偶 | 不是A是B、有人…可我想说… | `contrast` 左右对照 |
| 因果与循环 | 结果…、所以…、又回到 | `chain` 箭头链、`loop` 闭环 |
| 定义与拆解 | 它指的是… | `branch` 分支、`panel` 步骤面板 |

19 个单元共用 8 个形态，所以不用写 19 个组件。

## 四、用口播原话锚定起止，不写死秒数

单元表用**口播原话**定位，脚本去审稿里找那句话的 `finalRange`，算出起止和帧数：

```js
const at = (needle, which) => segments.filter(s => s.text.includes(needle))[0].finalRange[which];
{ from: at("也是在这个反思的过程当中", "start"), to: at("还是 AI 牛逼呢", "end") }
```

好处是审稿只要重算，时码自动跟着走；写死秒数会在下一次剪辑后全部错位。

## 五、写完先做冲突检查，再进工程

单元表生成时同时算每个窗口与画面运动的重叠秒数，任何一个大于 0.05 秒就打回：

```text
V018-17  panel     719.2s +79.9s   运动重叠 4.934s   ← 角落面板，记为显式例外
V018-18  contrast  812.0s +16.0s   运动重叠 3.529s   ← 起点后移到 815.6 秒
```

**角落常驻面板与全幅压暗不是一回事**：全幅压暗加图形在推近时是"突然出现抢焦点"，角落面板一直在场，不构成同一问题。这一条例外要显式写进检查脚本，不能默默放过。

## 六、写进 Cap 工程

```bash
# 1) 每个形态注册一次 definition（时长单位是秒，min 0.1 / max 3600）
cap-cli motion definition register <proj> --expected-revision N \
  --id work018-<kind> --version 1 \
  --source <workspace>/src/works/Work018.tsx \
  --composition-id Work018Overlay \
  --min-duration 0.1 --default-duration <秒> --max-duration 3600

# 2) 每个单元加一段
cap-cli motion add <proj> --expected-revision N \
  --definition-id work018-<kind> --definition-version 1 \
  --segment-id V018-xx --start <秒> --duration <秒>

# 3) 传内容 props
cap-cli motion props set <proj> --expected-revision N \
  --segment V018-xx --props-json '<单元内容>'

# 4) 渲染
cap-cli motion render <proj> --expected-revision N \
  --segment V018-xx --quality final --workspace <workspace>
```

每一步都用 `--expected-revision` 串行推进，revision 从 9 走到 75。全程校验源工程 revision 进入前后一致。

## 七、踩过的四个坑

**一、`motion` 的时长单位是秒，不是帧。** 我第一次按帧注册（min 60 / max 1200），`motion add --duration 8.8` 直接报 `DurationOutOfBounds`。而且注册过的 definition 不能覆盖 v1、`motion resize` 仍按 v1 的边界校验——**只能重建工作工程**。注册前先确认单位。

**二、Remotion 组件的常量漏声明会静默失败。** 重写组件时漏了 `FRAME_WIDTH / FRAME_HEIGHT / FPS` 三个常量，渲染报 `ReferenceError: FRAME_WIDTH is not defined`，但错误信息藏在渲染器退出码里，只看到 `Remotion renderer exited with status 1`。改完组件先单独渲一段验证，再批量渲。

**三、取产物要取最后一个。** 同一个 segment 重渲后 `motion.artifacts` 里会有多条记录，`[0]` 是旧版。抽帧验收时必须取 `[-1]`，否则看到的还是上一版画面。

**四、动画节奏要按口播报号的真实时刻，不能均分。** 步骤面板第一版按总时长均分，10 条在 17 秒内落满，而老胡报"第十步"是在 77.9 秒——完全脱节。改成每条传 `at`（相对单元开头的秒数），落地时刻直接对齐他报"第 N 步"的那一刻：

```text
第 4 步  0.00s      第 7 步  64.15s
第 5 步  35.31s     第 8 步  74.79s
第 6 步  59.60s     第 10 步 77.87s
```

## 八、留人机制怎么落到图形上

**不显示总数。** 面板只渲染已经落地的条目，容器自己往下长，观众看不到"一共几个"，只能一条一条数着往下等——这就是期待感的来源。

落地的条目里，最近一条高亮、其余压暗，于是面板同时承担**进度指示**：一直在演示，但观众始终知道"现在讲到第几步"。

这就是后半段"画面一直在动、但没有主线"的解法：主线不在画面上，在观众心里的那个计数器上。
