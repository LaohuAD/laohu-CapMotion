# 018 放大阶段画面抖动：测量与结论

对象：成片 `/Volumes/Laohu_Work/软件数据/Cap/录制/018_从使用AI工具到建立判断力_成片.mp4`
反馈：「在放大的阶段，画面会抖动；有时候我没怎么动，它也在抖。」

## 一、我做了什么

相位相关法测逐帧全局位移：把画面降到 160×90 灰度，用 FFT 求相邻两帧的整像素位移量，再乘回 1920 宽度。

- **全片 43,645 帧，逐帧测量**
- 判据：相邻两帧位移方向相反、且两帧幅度都落在 0.5–40 像素之间（真实抖动不会是大平移）

```text
全片方向反转候选：0 处
```

单独把 19 个推近窗口（合计 343.5 秒、10,300 帧）再测一遍，位移全部是同向的平滑推移，没有任何来回摆动。

## 二、看起来像抖的两处，是测量假象

扫描中只有两个异常点：

```text
685.27 秒   dx = -288 px，前后帧全为 0
1028.67 秒  dx = -128 px，前后帧全为 0
```

两个值恰好都是整数倍（240 宽下的 36 和 16 像素 × 8），孤点，左右邻帧位移为零，而同位置的纵向位移是平滑的 -8 / -16 / -16 / -16。这是相位相关在画面大幅换页时把峰值锁到了错误整数位，**不是画面真的跳了**。

## 三、结论

**导出成片里没有抖动。** 画面层在全部推近段的位移是单调、连续的，符合"平稳丝滑"。

所以看到抖动的位置不在成片，候选是三处：Cap 编辑器预览、播放器缩放窗口、更早的一版导出。

## 四、你猜的机制，方向是对的

源工程里每个推近段都带一套跟随相机配置：

```json
"manualFollow": {
  "x": 0.443, "y": 0.231,
  "config": {
    "comfortZoneRatio": 0.35,      // 舒适区：光标在里面，相机完全不动
    "outerGuardRatio": 0.75,       // 外护栏：光标出了这里，相机快速追
    "slowResponse": 18.0,          // 舒适区外、护栏内：慢速跟随
    "fastResponse": 32.0,          // 出护栏：快速跟随
    "predictionHorizonSecs": 0.1,  // 预测提前量
    "maxLeadRatio": 0.2
  }
}
```

你说的「可移动区域太小、移出某个边界整个方框就跟着动」——就是这个**舒适区加护栏**的结构。舒适区只有可视范围的 35%（中心往两侧各约 17.5%）。光标停在舒适区边缘时，手的微小抖动会让它反复进出边界，相机就在"按住"和"跟一下"之间来回切换；而慢速跟随 18 与快速跟随 32 之间是两档而不是连续过渡，切换本身带一个可见的顿挫。

**我没能读到渲染器源码**（这台机器上没有 Cap 源码仓库），所以上面是按配置字段和你的描述推断的机制，不是读代码确认的结果。

导出成片为什么反而干净：导出按固定 1/30 秒步进跟随相机，编辑器预览按真实帧间隔步进，两者对同一个弹簧积分出来的轨迹不同。

## 五、下次录音时怎么避免

如果重录同一类内容，改这几个值就能明显稳住：

| 字段 | 现在 | 建议 | 作用 |
| --- | --- | --- | --- |
| `comfortZoneRatio` | 0.35 | 0.5–0.6 | 舒适区加大，手抖不容易触发跟随 |
| `fastResponse` | 32.0 | 20–22 | 快速跟随放缓，与慢速档差距变小 |
| `slowResponse` | 18.0 | 12–14 | 慢速跟随再慢一点，减少启停 |
| `predictionHorizonSecs` | 0.1 | 0.05 | 预测提前量减半，减少过冲 |
| `maxLeadRatio` | 0.2 | 0.1 | 前导幅度减半 |

另一条更彻底的路：**推近时不去动鼠标**。只要光标在整个推近段里待在舒适区内，相机就完全静止，抖动的前提就不存在。

# 第二轮：源码级排查

## 找到了一个真实缺陷（但它不是这个抖动的成因）

`crates/rendering/src/cursor_interpolation.rs` 的 `interpolate_raw_cursor` 名字叫插值，
实际在两个采样点之间**直接返回左端点坐标**，不连线——光标位置是阶梯函数。
同时它又按整段平均算 `velocity`，返回值与自身的速度字段互相矛盾。

跟随相机每帧读两处位置：当前与 `+prediction_horizon_secs`（0.1 秒）。本片光标采样约 7 点/秒
（间隔 143 毫秒），比预测窗口还长，于是"未来位置"经常整级跳变，提前量与响应档位随之跳。

**已修复**：采样间隔内线性插值；间隔超过 500 毫秒时不连线（移动事件流的长间隔表示光标没动，
把两点连成缓慢直线会让相机凭空平移）。新增三个测试，`cargo test -p cap-rendering` 11 项全过。

**实测结论：这个修复对抖动没有任何影响。** 用带修复的二进制重导同一工程，逐帧横移量完全一致：

```text
区间              修复前(标准差/峰谷/猛推帧)   修复后
196–208 秒          5.47 / 35 / 62       →     5.50 / 35 / 62
218–222 秒          3.58 / 19 / 41       →     3.58 / 19 / 41
1135–1143 秒        8.34 / 62 / 106      →     8.29 / 61 / 111
```

所以它是一条独立的正确性修复，不是本症状的根因。可以单独回滚，不影响其他行为。

## 测量本身被拖影污染了

把 199.00–199.74 秒的连续帧拼成对照图直接看：199.0–199.2 的三帧画面**明显是重影拖糊的**，
199.268 之后才变清晰。工程里 `screenMotionBlur: 1.0`，相机一动就给画面加方向性模糊。

一维列剖面相关会把这种不对称的拖影读成"位移"，所以此前测到的 ±20–62 像素横移里，
有多少是真实位移、有多少是拖影造成的读数偏差，**目前分不开**。

## 现在的状态

- 现象确实存在：107 段、约 145 秒的时间里画面出现爆发式变化
- 已确认不是光标插值缺陷造成的
- 画面移动与光标数据在时间上是吻合的（198.28–199.57 光标从 x=0.475 扫到 0.309，
  相机同向跟随）——**这说明至少有一部分"抖动"其实是相机在正常跟随光标**
- 拖影把真实位移的读数放大了，需要先把模糊关掉再测一次，才能把两者分开

## 下一步该怎么查

1. 复制工程并设 `screenMotionBlur: 0`，重导同一区间，用同一套逐帧测量对比——
   两者之差就是拖影贡献的部分
2. 拖影剥离后再看剩余位移是否仍有"推出去又退回来"的往复；若有，才回到跟随相机参数
3. 若能拿到实拍观看的屏幕录像，与逐帧数据对齐，可以直接定位到具体是哪一种运动被看成了抖动
